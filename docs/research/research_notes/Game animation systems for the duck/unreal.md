# Unreal Engine 5 character animation architecture (as of 2026) — mechanisms, layers, and what each one is for

Scope note: these are research notes for a robotics engineer who wants to borrow UE5's structure for a small physical biped. Facts are cited inline; anything marked "Inference" is my interpretation. Epic's current docs pages are labelled "Unreal Engine 5.8 Documentation" (fetched 2026-11-05); where a feature's introduction version matters I cite a versioned API page. Several Epic user-guide pages (Inertialization, Physical Animation, Look At, Leg IK) returned empty bodies to the fetch tool; for those I fall back to Epic's Python/C++ API reference pages and to secondary sources, and I say so.

## 1. Core pipeline: Animation Blueprint, AnimGraph vs EventGraph, state machines, blends, layers, slots, sync, root motion, notifies, poses, curves — and how it is evaluated each frame

### Takeaway
An Animation Blueprint (AnimBP) is split into a game-thread EventGraph (gathers state) and a worker-thread-capable AnimGraph (a tree of pose-producing nodes evaluated once per tick to one Output Pose). State machines, blend spaces, additive/aim-offset layers, Layered-blend-per-bone, Slots (for Montages) and Linked Anim Layers are all just nodes in that tree; each contributes a weighted pose plus blended curves and (optionally) root-motion deltas, and zero-weight branches are not evaluated.

### Cited Findings

**Two graphs, three phases**
- An Animation Blueprint has an EventGraph that handles state and an AnimGraph that produces the pose; "Initialization runs once, while update and evaluate run every tick," the EventGraph is updated first so the AnimGraph has current variable values, and Evaluate is the step that yields the final pose — [Epic blog, Animation Blueprints (2014, UE4-era but still the model)](https://www.unrealengine.com/en-US/blog/animation-blueprints)
- Epic 5.8 docs: "Animation Blueprints are visual scripts that are used for the creation and control of complex animation behaviors"; the graph "blend[s] animation, control[s] a Skeleton's bones, or create[s] logic that defines the final pose per frame"; a mesh must have Animation Mode = Use Animation Blueprint and an Anim Class assigned — [Epic docs, Animation Blueprints](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprints-in-unreal-engine)
- The Event Graph runs on the Game Thread once per Tick and is "generally the most expensive part"; logic moved into Thread Safe functions (override `Blueprint Thread Safe Update Animation`, per-function `Thread Safe` flag) runs on Worker Threads; such functions cannot touch non-thread-safe objects directly and use `Property Access` nodes/pins instead. Conditions that force a game-thread update are in `UAnimInstance::NeedsImmediateUpdate`; root motion blocks parallel updates because "character movement is not multi-threaded." The remaining game-thread work (`FParallelAnimationCompletionTask`) includes physics updates, animation notifies, URO interpolation and curve blending — [Epic docs, Animation Optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-optimization-in-unreal-engine)
- Fast Path: a node pin that is a plain member variable (or negated bool / nested struct member) avoids the Blueprint VM; any calculation on a node input disables Fast Path for that node; `Warn About Blueprint Usage` flags VM calls in the AnimGraph — [Epic docs, Animation Optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-optimization-in-unreal-engine)
- Update Rate Optimization (URO): "Enable Update Rate Optimizations" on the Skeletal Mesh Component; Epic recommends 15 Hz or lower at suitable distances, or the Animation Budget Allocator plugin — [Epic docs, Animation Optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-optimization-in-unreal-engine)
- Lyra moves per-frame math into `BlueprintThreadSafeUpdateAnimation` and uses Anim Node Functions `On Initial Update`, `On Become Relevant`, `On Update` on nodes/states (e.g. `UpdateIdleState` under State Node Functions); legacy state-machine events fired after the animation update in older engine versions — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)

**State machines and transitions**
- Each state "has its own Anim Graph layer and a final Output Pose. Its logic runs only while the state is active." Transitions are single-direction; Conduits give 1-to-many / many-to-1 / many-to-many routing (their rules return false by default); State Aliases consolidate transitions, and a Global Alias lets all states transition into it (Epic recommends limiting it to single-frame inputs and finite-duration states such as attacks). State-machine properties: `Max Transitions Per Frame` ("how many transitions or decisions can occur in a single frame or tick"), `Skip First Update Transition`, `Reinitialize on Becoming Relevant`, `Create Notify Meta Data`, `Allow Conduit Entry States`; `Always Reset on Entry` restarts sequence players on entry; `Entered/Left/Fully Blended State Event` emit Skeleton Notifies — [Epic docs, State Machines](https://dev.epicgames.com/documentation/en-us/unreal-engine/state-machines-in-unreal-engine)
- Transition rules output a boolean; "If multiple transitions are true at the same time, the one with the smallest priority is chosen" (`Priority Order`); `Bidirectional` "is unsupported and currently does not function"; `Automatic Rule Based on Sequence Player in State` triggers from the most relevant asset player's remaining time, with `AutomaticRuleTriggerTime` (<0 uses `AnimationLength - CrossFadeDuration`). Transition-graph functions: `Current State Time`, `Get Relevant Anim Time`, `Get Relevant Anim Time Remaining`, `Time Remaining`, plus notify queries (`Was Anim Notify Name Triggered…`, `Was Anim Notify State Active…`) scoped to any/source state/state machine. `Blend Logic` is `Standard Blend` | `Inertialization` | `Custom`; Standard Blend has `Duration`, `Mode` (curve type), `Custom Blend Curve`, `Blend Profile` ("Lets specific bones blend at different speeds") and `Transition Crossfade Sharing`; Custom blend graphs read `State Weight`, `Get Transition Time Elapsed (ratio)`, `Get Transition Crossfade Duration`. Transition Interrupt: another state becoming active mid-blend redirects the blend; Start/End/Interrupt transition events exist — [Epic docs, Transition Rules](https://dev.epicgames.com/documentation/en-us/unreal-engine/transition-rules-in-unreal-engine)
- Epic's guidance on the Inertialization blend logic: "Carries velocity and acceleration forward. Requires the Inertialization node after the State Machine in the Anim Graph. Keep duration under about 0.4 seconds. Avoid it when poses differ greatly." — [Epic docs, Transition Rules](https://dev.epicgames.com/documentation/en-us/unreal-engine/transition-rules-in-unreal-engine)

**Blend nodes, additive, layered-per-bone, blend weights**
- Blend nodes take an `Alpha`: "An alpha value of zero will typically favor the primary pose, while a value of 1 will favor the secondary pose." `Apply Additive` / `Apply Mesh Space Additive` add an additive pose to a base pose by alpha; `Make Dynamic Additive` subtracts (optionally in Mesh Space); `Blend Poses by bool/int/Enum` each carry per-pose float `Blend Time` and a `Transition Type` (standard or Inertialization); `Layered blend per bone` takes a base pose plus N blend poses, mode `Branch Filter` (Bone Name + Blend Depth, tapering weights down the hierarchy) or `Blend Mask`, `Mesh Space Rotation Blend` / `Mesh Space Scale Blend`, `Curve Blend Options` (Override, Do Not Override, Normalize by Weight, Blend by Weight, Use Base Pose, Use Min/Max Value) and `Blend Root Motion Based on Root Bone` — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine)
- Lyra's "Upperbody/lowerbody split" is a `Layered blend per bone` with Blend Masks, combining full-body locomotion (e.g. jog_fwd) with upper-body weapon fire/reload — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)

**Blend Spaces (1D/2D) and Aim Offsets**
- Asset types `Blend Space`, `Blend Space 1D`, `Aim Offset`, `Aim Offset 1D`; each axis has Name/Min/Max, `Grid Divisions`, `Wrap Input` (circular axis), `Axis to Scale Animation` (which axis scales playback speed when `Smoothing Time` is used, typically speed). Sample weighting is by triangulation by default (`Preferred Triangulation Direction`: None/Tangential/Radial) or legacy `Use Grid`. Input smoothing: `Smoothing Time`, `Smoothing Type` (Averaged, Linear, Cubic, Ease In/Out, Exponential, Spring Damper), `Damping Ratio`, `Max Speed`; sample-weight rate limiting via `Weight Speed` and `Per Bone Overrides`. Aim Offset samples are "mesh-space additive animations"; `Notify Trigger Mode` = All Animations / Highest Weighted Animation / None — [Epic docs, Blend Spaces](https://dev.epicgames.com/documentation/en-us/unreal-engine/blend-spaces-in-unreal-engine)

**Linked Anim Graphs / Linked Anim Layers / Layer Interfaces**
- `Linked Anim Graph` node (category "Linked Anim Blueprints") has `Instance Class`, `Receive/Propagate Notifies from/to Linked Instances`; `Input Pose` nodes become pose input pins. An `Animation Layer Interface` asset declares named layers (read-only graphs); a base AnimBP binds it under Class Settings > Interfaces and places the layers in its AnimGraph; specific AnimBPs implement the layers; the `Link Anim Class Layers` node (Target = Skeletal Mesh component, In Class = specific AnimBP) swaps implementations at runtime and "overwrites the current layer logic." Layers sharing a non-default `Group` name share one Animation Instance. Fortnite runs two interfaces (weapons, vehicles) at once; unconnected layer outputs leave the base pose unchanged; only linked AnimBPs load, but unloading is not automatic — [Epic docs, Animation Blueprint Linking](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-linking-in-unreal-engine)
- Inertial-blend request sources include linked/layered AnimGraphs' `Graph Blending` section; "Negative blend values defer timing to the other incoming or outgoing layer" — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine)

**Slots and Montages**
- Montages are divided into `Montage Sections` playable in any order; sequences are organized into `Slots` and `Slot Groups`; "A Slot occupies a mesh or part of a mesh and is played in the Animation Blueprint through that Slot"; the doc's example is separate upper-body and lower-body slots; sequences in the same Slot/Group "will override playback of any other sequence when triggered"; Child Montages override sequences with auto-adjusted play rate; networked play requires manually replicating PlayMontage via RPC — [Epic docs, Animation Montage](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-montage-in-unreal-engine)
- Montage-specific notifies: `Montage Notify`, `Montage Notify Window`, `Disable Root Motion` state; `Montage Tick Type` = `Queued` (async, less precise, cheaper) or `Branching Point` (synchronous, frame-accurate, higher cost, "suited to gameplay-altering branching") — [Epic docs, Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine)
- Lyra: Montages support Blend Profiles and Inertialization, but enabling both at once was "not supported in 5.0" — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)

**Sync Groups and Sync Markers**
- Leaders set the group's master length and have priority for notifies; followers match the leader's length with notifies suppressed; by default "The animation with the highest blend influence becomes the leader." `Group Role`: `Can be Leader` (default), `Always Follower`, `Always Leader`, `Transition Leader`, `Transition Follower` (the Transition roles are excluded from syncing while blending in). `Sync Method`: `Do Not Sync`, `Sync Group`, `Graph`. Marker-based sync is used automatically when animations share markers (only markers present in all members are used; e.g. "Right Foot Down"); otherwise it falls back to normal length-based syncing. Use cases: mismatched step counts/stride lengths; starts and stops should be `Always Leader`. Blend Space Graphs propagate sync to child samples. Restriction: synced clips should share the same general body movement (same planted feet at first/last frames); large length differences cause playrate "pops" when leader/follower switch — [Epic docs, Sync Groups](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-sync-groups-in-unreal-engine)
- Notify `Trigger on Follower` exists because "By default only leaders fire" — [Epic docs, Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine)

**Root motion vs in-place**
- Root Motion "lets animation data drive character movement"; per-asset `Enable Root Motion`; `Root Motion Root Lock` = Ref Pose / Anim First Frame / Zero; `Force Root Lock`; AnimBP `Root Motion Mode` = `No Root Motion Extraction` | `Ignore Root Motion` | `Root Motion from everything` ("extracted from every enabled asset contributing to the pose, blended by each asset's weight") | `Root Motion from Montages Only`. "The two extraction modes move Animation Graph updates to the Game Thread instead of a Worker Thread." During playback the animation drives the Movement Component; when Walking or Falling the Z of root motion is ignored and gravity applies; when Flying full root motion applies — [Epic docs, Root Motion](https://dev.epicgames.com/documentation/en-us/unreal-engine/root-motion-in-unreal-engine)
- The Animation Warping plugin also ships a "Root Motion Delta animation attribute" (root motion carried as a per-frame attribute through the graph) — [Epic API, AnimationWarping plugin index](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/PluginIndex/AnimationWarping)

**Notifies**
- `Notify` fires one event at a keyframe; `Notify State` spans a duration with `Received Notify Begin / Tick / End`. Built-ins: Play Sound, Play Niagara/Particle Effect, Clothing Simulation pause/resume/reset, `Reset Dynamics` (restores AnimDynamics), `Skeleton Notify` (custom event stored on the Skeleton), timed Niagara (with Anim Curve Parameters mapping curves to Niagara floats), Trail, `Sync Marker`. Trigger rules: `Trigger Weight Threshold` (default 0.00001), `Notify Trigger Chance`, `Trigger on Dedicated Server`, `Trigger on Follower`, `Notify Filter Type` by LOD — [Epic docs, Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine)
- Notifies fire on the game thread as part of the post-parallel completion task — [Epic docs, Animation Optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-optimization-in-unreal-engine)

**Pose Assets and Curves**
- Pose assets are "stored skeletal mesh poses," one or many, "saved as animation curves within the asset"; generating from a sequence yields a pose per frame; `Additive` + `Convert to Additive Pose` makes them layerable; runtime nodes are `Pose Blender` and `Pose Driver` — [Epic docs, Pose Assets](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-pose-assets-in-unreal-engine)
- Animation Curves are "float-type values you can add and keyframe within an Animation Sequence," stored on the Skeleton; `Type` flags drive Morph Targets or Material scalar parameters by name; in AnimBPs "Curves can drive arbitrary values, often IK alpha values" via `Get Curve Value`, `Get Active Curve Names`, `Get All Curve Names`; `Metadata Curve` outputs a constant 1.0 (0.0 when absent) as a cheap per-clip flag; `Connected Bones` and `Max LOD` gate evaluation — [Epic docs, Animation Curves](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-curves-in-unreal-engine)
- Curve blending across the graph is explicit: the `Layered blend per bone` node's `Curve Blend Options`, and Inertialization/Dead Blending nodes have `Filtered Curves` lists for curves that must switch instantly — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine)
- Animation Modifiers are native or Blueprint classes that apply "a sequence of actions" to a sequence or skeleton (`OnApply`/`OnRevert`), e.g. generating foot sync markers from ground-contact frames; Animation Blueprint Library functions include Add Float Curve Keys, Add Animation Notify Events, Add Animation Sync Markers, Get Bone Pose(s) for Frame/Time (local space), Find Bone Path to Root — [Epic docs, Animation Modifiers](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-modifiers-in-unreal-engine)

**Pose caching and relevancy (evidence)**
- Inertialization/Dead Blending nodes expose `forward_requests_through_skipped_cached_pose_nodes`: forwards requests "through downstream UseCachedPose nodes whose update was skipped … useful in the case where the same cached pose is used in multiple places" — confirms Save Cached Pose / Use Cached Pose nodes and that cached-pose updates can be skipped — [Epic Python API, AnimNode_Inertialization](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_Inertialization); [Epic Python API, AnimNode_DeadBlending](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_DeadBlending)
- "Once active, the source pose is no longer evaluated" (Inertialization node) and state logic "runs only while the state is active" — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine); [Epic docs, State Machines](https://dev.epicgames.com/documentation/en-us/unreal-engine/state-machines-in-unreal-engine)
- Nodes have `On Become Relevant` / `On Initial Update` hooks and transitions query "the most relevant animation" — i.e. relevancy (non-zero weight) is a first-class concept — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine); [Epic docs, Transition Rules](https://dev.epicgames.com/documentation/en-us/unreal-engine/transition-rules-in-unreal-engine)
- Per-node `LOD Threshold` ("Max LOD that this node is allowed to run") on skeletal controls — [Epic Python API, AnimNode_LookAt](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_LookAt)
- Skeletal control (bone-modifying) nodes "operate and compute transforms in the Component Space," and "a float value between 0.0 and 1.0 is used as the alpha value to determine the weight of the applied Skeletal Transform" — [Epic docs, Skeletal Controls](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-skeletal-controls-in-unreal-engine)

### Inferences
- Per-frame order, assembled from the sources: (1) game-thread EventGraph / native update gathers inputs; (2) AnimGraph Update pass walks the tree root-to-leaf, advancing asset-player time, ticking state machines (at most `Max Transitions Per Frame` decisions), computing blend weights and sync-group leader/follower times, and marking which branches are relevant; (3) AnimGraph Evaluate pass pulls poses leaf-to-root, each node producing local-space (or component-space for skeletal controls) bone transforms plus a curve set and, when enabled, a root-motion delta; cached poses are evaluated once and reused; (4) back on the game thread, notifies, root-motion consumption by the movement component, curve blending to morphs/materials, and physics happen in the completion task. The 2014 blog states (1)-(3) at the level of "update EventGraph, update AnimGraph, evaluate"; the exact Update/Evaluate split is my reading of the node property names (`internal_time_accumulator`, `blend_weight`) and the optimization page.
- Zero-weight branches are skipped entirely (the Inertialization doc's "source pose is no longer evaluated" and the `On Become Relevant` hooks only make sense if weight-zero branches are not ticked). The weight threshold constant is not stated in any page I fetched.
- Root motion is best thought of as another blended channel: "from everything" blends deltas by asset weight; `Layered blend per bone` has an explicit root-motion weighting option; the Animation Warping plugin moves it into a per-frame attribute so nodes downstream (orientation warping, motion matching) can read it.

### Gaps
- Epic's AnimGraph evaluation-order page itself (Save Cached Pose / Use Cached Pose node docs, the exact relevancy threshold, local vs component-space conversion nodes) was not reachable in this session; the above is reconstructed from adjacent pages.
- The Transition Rules page does not enumerate the `Mode` curve types (Linear/Cubic/Hermite/Sinusoidal/…); the Blend Stack API lists `blend_option` as an `AlphaBlendOption` enum but the doc page does not list its values.
- Montage blend-in/out settings (Blend In/Out time, `Blend Option`, `Blend Profile`, `Inertialization` blend mode) are not on the Montage page fetched; only the Lyra page confirms Montages support Blend Profiles and Inertialization.

## 2. Transition quality: Inertialization (Bollo, GDC 2018), Dead Blending (Holden), blend profiles, crossfade types — and why inertialization replaced crossfades

### Takeaway
A crossfade evaluates both source and destination for the whole blend; inertialization instead records, at the switch, the pose/velocity offset between the last output and the new animation and decays that offset to zero as a post-process, so only the destination is evaluated afterwards. Dead Blending (UE 5.3, "stable" from 5.4) keeps a crossfade but extrapolates the source clip forward with exponentially decaying velocity, which handles large pose differences better. Blend Profiles let specific bones blend faster or slower than the rest.

### Cited Findings
- GDC 2018 talk description (David Bollo, Microsoft, "Inertialization: High-Performance Animation Transitions in Gears of War"): conventional transitions blend old and new states, so both are evaluated during the blend, "effectively doubling the animation evaluation cost"; the team "eliminated these blended transitions altogether" and handled transitions "as a post-process with a technique called 'inertialization'"; the talk covers the math "for both vector and quaternion values" and how to add it to an existing engine — [GDC Vault](https://www.gdcvault.com/play/1025331/Inertialization); [Game Developer summary](https://gamedeveloper.com/art/video-high-performance-animation-transitions-in-i-gears-of-war-i-); earlier SIGGRAPH 2017 sketch "High Performance Animation in Gears of War 4" — [SIGGRAPH history](https://history.siggraph.org/person/auto-draft-642)
- Holden's formulation of the same idea: at a transition compute the offset between the (previous output) and destination, `off_x = (dec_x + src_x) - dst_x`, likewise for velocity; "The offset then decays to zero over the blend time, using either a critically damped spring or a cubic polynomial. The output is the incoming animation plus the decayed offset." The spring variant stores initial offset/velocity and elapsed time; its transition "cost" (area between curves) is `(2xy + v)/y²` for half-damping y, offset x, velocity v, which yields a per-bone motion-matching feature `2·pos/y + vel/y²` — [Holden, Inertialization Transition Cost](https://theorangeduck.com/page/inertialization-transition-cost)
- Epic's Inertialization node: "Post-process blend. Once active, the source pose is no longer evaluated." Activated by inertial blend requests from anything upstream on its `Source` pin (blend nodes with `Transition Type = Inertialization`, state-machine transitions with `Blend Logic = Inertialization`, linked/layered graphs' `Graph Blending`); "With multiple requests, the minimum requested blend duration is used"; it "Records the offset between incoming and outgoing animations and fades it out"; properties `Blend Profile` and `Filtered Curves`; it "Ignores transition blend curves"; a missing node logs a runtime error — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine)
- Node properties: `default_blend_profile`, `filtered_bones` ("These bones will change instantly when the animation switches"), `filtered_curves`, `forward_requests_through_skipped_cached_pose_nodes`, `reset_on_becoming_relevant`, `preallocate_memory` (deprecated) — [Epic Python API, AnimNode_Inertialization](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_Inertialization)
- Epic's practical limits for inertialized transitions: "Keep duration under about 0.4 seconds. Avoid it when poses differ greatly." — [Epic docs, Transition Rules](https://dev.epicgames.com/documentation/en-us/unreal-engine/transition-rules-in-unreal-engine)
- Holden's critique of inertialization (motivation for dead blending): offset-based inertialization "requires both the source and destination animations to be evaluated (and their velocities) on the frame of transition," and can cause "knee pops and floaty, swimming motions" — [Holden, Dead Blending](https://theorangeduck.com/page/dead-blending)
- Dead blending mechanism: the source clip is extrapolated "forward in time… past the point of transition" and a normal cross-fade is inserted between that extrapolation and the destination; per joint, position += velocity·dt, rotation advanced by a scaled-angle-axis angular-velocity quaternion; velocity decays as `exp(−ln2·dt/halflife)`; blend weight `alpha = smoothstep(ext_t / blendtime)`; the name is "due to its resemblance to dead reckoning"; it "only needs the current pose and, at transition, its velocity, which can be tracked with finite differences." Limitations: long blends make extrapolations produce "crazy poses" (jitter, over/under-rotation even at 0.2 s); versus crossfade it still has "mushiness and foot sliding"; versus inertialization it should reduce knee pops but "damps destination details" — [Holden, Dead Blending](https://theorangeduck.com/page/dead-blending)
- Epic's Dead Blending node: "Predicts future poses of the outgoing animation and blends them with the incoming animation. Often performs better with large pose differences, but can look stiffer. Respects transition blend curves." Properties include `Extrapolation Half Life` (+min/max), `Maximum Translation Velocity` (default 500.0 cm/s), `Maximum Rotation Velocity` (360.0 deg/s), `Maximum Scale Velocity` (4.0), `Maximum Curve Velocity` (100.0), `Filtered Bones/Curves`, `Blend Time Multiplier`, `Show Extrapolations`; the doc page still labels it experimental — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine); API text: it "extrapolates the animation being transitioned from forward in time," then cross-fades; "The decay rate is set automatically from how the source velocities relate to the target pose"; `extrapolation_half_life_min` is used "when the velocities of the animation being transitioned from are very small" or moving away from the target — [Epic Python API, AnimNode_DeadBlending](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_DeadBlending)
- Holden on the UE implementation: the node ships in "Unreal Engine 5.3" as "experimental," is "a drop-in replacement for the standard Inertialization node," stores the pose at the moment of transition and uses an implicit extrapolation function; a per-axis half-life heuristic clamps a scaled ratio of (source−destination difference)/(source velocity) between `halflife_min` (0.1) and `halflife_max` (1.0) with `halflife_scale` 0.3; axes moving slowly toward the destination extrapolate long, axes moving fast or away get short half-lives — [Holden, Dead Blending Node in Unreal Engine](https://theorangeduck.com/page/dead-blending-node-unreal-engine)
- Community report: Dead Blending "is stable and was removed from experimental status in May 2024" (forum reply; the 5.8 Blend Nodes doc page still carries an experimental label, so sources conflict) — [Epic forums](https://forums.unrealengine.com/t/stability-of-the-dead-blending-node-in-animation-workflows/2670429)
- Game Animation Sample uses Dead Blending in its `Simple Aim Offset` layer — [Epic docs, Game Animation Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-animation-sample-project-in-unreal-engine)
- Blend Stack node (BlendStack plugin, documented from 5.3): a stack of concurrently blending anim players; `max_active_blends` ("If MaxActiveBlends is zero then blend stack is disabled"), `store_blended_pose` (overflow accumulates into a stored pose, otherwise "blendstack will start discarding animations, potentially resulting in animation pops"), `max_blend_in_time_to_override_animation`, `blend_time`, `blend_profile`, `blend_option`, `use_inertial_blend`, `mirrored` + `mirror_data_table`, `notify_recency_time_out`, `player_depth_blend_in_time_multiplier` — [Epic Python API, AnimNode_BlendStack 5.4](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_BlendStack?application_version=5.4); earliest doc page found is 5.3 — [Epic Python API, AnimNode_BlendStack 5.3](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_BlendStack?application_version=5.3)

### Inferences
- Why inertialization won: (a) cost — the source need not be evaluated after the switch frame, which matters when a state machine would otherwise keep whole sub-graphs alive; (b) quality — the decayed offset preserves velocity continuity, so the character "carries momentum" through the switch instead of lerping between two moving targets (which produces the classic mid-blend foot-slide and limp look); (c) simplicity — it works for any switch (state, layer link, montage) because it only looks at the output pose stream, which is why UE puts a single Inertialization node after the state machine rather than per-transition logic.
- Math idea (my recollection of Bollo's slides, NOT verified in this session, see Gaps): for each bone component form the offset x0 = previous_output − new_pose and offset velocity v0, pick blend time t1 (shortened to −5·x0/v0 when the offset is already heading toward zero so it cannot overshoot), set a0 = (−8·v0·t1 − 20·x0)/t1², and decay with a quintic x(t) = A t⁵ + B t⁴ + C t³ + (a0/2) t² + v0 t + x0 whose position, velocity and acceleration are all zero at t1; rotations use the scaled angle-axis of the offset quaternion. Holden's cubic/spring form above is the sourced equivalent.
- For a robot the relevant distinction is: inertialization = "remember an offset, let it decay" (one pose + one velocity of state, no second trajectory needed); dead blending = "keep running the old trajectory forward with damping, crossfade to the new one" (needs the old trajectory's velocity but no second controller); crossfade = run both. The engine's default velocity clamps (500 cm/s, 360 deg/s) are the kind of safety caps a robot would set at actuator limits.

## 3. Adaptation mechanisms: Control Rig, IK Rig / Retargeter, Full-Body IK, Two-Bone IK, Leg IK, Foot Placement, Orientation/Stride/Slope warping, Motion Warping, Distance Matching, turn-in-place, Character Movement / Mover interplay — how feet stay planted and hands reach ledges

### Takeaway
UE separates "what the clip says" from "what the world needs" with a stack of post-process nodes: pose-warping nodes (Orientation/Stride/Slope) re-aim and re-scale the authored stride to the capsule's actual direction and speed; Distance Matching re-times starts/stops/landings to measured distance; Motion Warping edits root motion so a montage lands on a target; Foot Placement / Leg IK / Two-Bone IK / Full-Body IK then pin end effectors to traced ground or sockets. Control Rig and IK Rig are the general-purpose solvers; IK Retargeter maps clips between skeletons.

### Inferences
- The canonical ordering Epic uses (from Lyra + GASP) is: pose source (state machine or motion matching) → distance matching / playrate (time) → orientation & stride warping (reshape the clip to measured heading/speed) → additive layers (lean, aim offset) → slot/montage overrides → foot placement / leg IK (pin feet to the traced ground) → physics-ish nodes last. Warping comes before IK because warping moves the IK foot targets and IK then solves the FK leg to them; the pose-warping docs explicitly need an IK Rig leg definition for that reason.
- "How feet stay planted": the clip carries IK foot bones (and optional foot-lock curves/markers); Stride/Orientation warping move those targets in the ground plane; Foot Placement / Leg IK trace the floor, lock the foot while a curve or root-motion attribute says it is planted, and pull the pelvis down (`Pull Pelvis Down`, `Pelvis IK Foot Solver`); Offset Root Bone lets the mesh lag the capsule so the planted foot does not slide when the capsule starts/pivots. "Hands on ledges": Motion Warping skews the montage's root motion so the whole body arrives where the hand-contact notify window expects, then Two-Bone IK/FBIK can fine-tune the hand to the surface.
- All adaptation nodes are parameterized by alphas and interpolation half-lives, which is how Epic blends "authored" and "adapted" smoothly rather than switching.

## 4. Motion Matching (PoseSearch plugin, UE 5.4+; Lyra; Game Animation Sample) — database, trajectory/pose features, schema, selection, what it replaced, costs, failure modes, Chooser tables

### Takeaway
Motion Matching is a per-frame nearest-neighbour search over a feature database built from a Pose Search Schema (trajectory samples at past/future offsets + bone position/velocity/rotation samples) against a query assembled from the predicted trajectory and the current pose history; the winning (asset, time) is played through a Blend Stack with inertial blending. It became production-ready in UE 5.4 after shipping on all Fortnite characters, replaces locomotion state machines/blend spaces, and uses Chooser tables to pick which databases are searchable.

### Cited Findings
- UE 5.4 (April 2024) promoted Motion Matching from Experimental to Production-Ready; it was "battle-tested in Fortnite Battle Royale" on all platforms, running on all 100 characters plus NPCs — [Epic blog, UE 5.4](https://www.unrealengine.com/en-US/blog/unreal-engine-5-4-is-now-available); trade coverage — [cgpress](https://cgpress.org/archives/unreal-engine-5-4-released.html)
- Epic defines it as "a query-based animation pose selection system," "a dynamic alternative to State Machines, or Blendspaces," working "without the need to set up transition or blending logic between Animation Sequences," and fidelity rises "by just adding more animation data to the Database asset" — [Epic docs, Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine)
- Pose Search Schema: Skeleton, Mirror Data Table, `Data Preprocessor` (None / Normalize / Normalize Only by Deviation), `Sample Rate`, Channels, `Number of Permutations`, `Permutations Time Offset`, `Add Data Padding`. Default channels are Trajectory and Pose with `foot_l` and `foot_r` sampled. Channel types: Trajectory (samples with `Offset` — positive = future, negative = past — Flags, Weight; sourced from the Character Trajectory component), Pose (Sampled Bones with Flags Velocity/Position/Rotation/Phase, `Use Character Space Velocities`), Heading, Position, Velocity, Phase, Padding (16-byte alignment), Sampling Time (debug), Group, Crashing Legs (experimental, thigh/foot tolerance). Query pose source: `Use Character Pose` / `Use Continuing Pose` / `Use Interpolated Continuing Pose`; `Component Stripping` None/Strip XY/Strip Z — [Epic docs, Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine); "the total query cost is the sum of the channel costs" — [Epic Python API, PoseSearchSchema 5.4](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/PoseSearchSchema?application_version=5.4)
- Pose Search Database: Animation Sequences (default), Composites, Blendspaces (Montages not supported in AnimBPs); locomotion sequences must have root motion enabled; `Continuing Pose Cost Bias` (negative favours staying), `Looping Cost Bias`, `Base Cost Bias`, `Exclude from Database Parameters`, `Additional Extrapolation Time`, Tags, Normalization Set; search modes `Brute Force`, `PCAKDTree` (Pose Pruning Similarity Threshold, Number Of Principal Components, KDTree Max Leaf Size, `KNNQuerryNumNeighbors` = how many candidates get full cost analysis), `VPTree` (experimental); "KD-tree results are approximate" — [Epic docs, Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine); [Epic Python API, PoseSearchDatabase 5.5](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/PoseSearchDatabase?application_version=5.5)
- Motion Matching node inputs: Database, `Blend Time`, `Blend Profile`, `Pose Jump Threshold Time`, `Pose Reselect History`, `Search Throttle Time`, `Play Rate`, `Use Inertial Blend`, `Max Active Blends` (0 disables the blend stack), `Store Blended Pose`, `Max Blend in Time to Override Animation`, `Player Depth Blend Time Multiplier`, `Should Search`, `Reset On Becoming Relevant`, `Should Use Cached Channel Data`, notify filtering (`Notify Recency Time Out` 0.2). Pose History node: `Generate Trajectory`, `Collected Bones`. Weights per channel/sub-property are normalized unless preprocessor is None; "Weights cannot fix poor coverage. Animation Warping and database sets are suggested alternatives." Costs: more channels/samples/data increase memory and CPU; "Too many samples can distort results"; higher Sample Rate raises memory — [Epic docs, Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine)
- GASP: Motion Matching node in `ABP_SandboxCharacter` takes a database and the trajectory query from the Pose History node; `Update_MotionMatching` evaluates a Chooser each frame to output an array of databases; `Update_MotionMatching_PostSelection` caches the selected database so its tags can be read; `Get_MMBlendTime` and `Get_MMInterruptMode` set blend time/interrupt from state changes; `GenerateTrajectory` builds the query trajectory from the Motion Trajectory Component; `IsMoving/IsStarting/IsPivoting` derive from current and future trajectory velocities; Chooser table `CHT_PoseSearchDatabases` filters databases by gameplay context ("walk databases are used only when the player walks"); motion matching also selects montages and entry frames for traversal; runtime `Motion Matching Database LOD` changes searched pose density — [Epic docs, Game Animation Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-animation-sample-project-in-unreal-engine)
- Chooser plugin (page labelled Experimental): `Chooser Table` with columns bound to AnimBP variables (examples: a bool `IsCrouching`, a numeric range −100…100), rows mapping to output assets (`Output Object Type` e.g. `AnimSequenceBase`), `Proxy Table`/`Proxy Asset` for swapping whole animation sets, `Evaluate Chooser` / `Evaluate Proxy` nodes (e.g. from a Sequence Player's `On Update`), context objects bound to the AnimBP class with Direction = Read; generic for "any type of Asset, Object, or Class" — [Epic docs, Dynamic Asset Selection](https://dev.epicgames.com/documentation/en-us/unreal-engine/dynamic-asset-selection-in-unreal-engine)
- UE 5.7 added "a new Experimental Pose Search Column in Choosers, which brings Choosers and Motion Matching closer together" — [Epic tech blog (search snippet)](https://www.unrealengine.com/en-US/tech-blog/explore-the-updates-to-the-game-animation-sample-project-in-ue-5-7)
- Holden on failure modes: motion matching "by default does not blend animation data, so exact velocities or turn angles often need correction"; data-coverage fixes include speeding mocap ~10% and mirroring; design guidance is to let animators label regions of data with desired displacement behaviour instead of embedding settings in states — [Holden, Code vs Data Driven Displacement](https://theorangeduck.com/page/code-vs-data-driven-displacement)
- Community critique of state machines that motion matching addresses: state machines "decide the routes in advance" whereas motion matching picks the best-fitting motion each moment — [uhiyama-lab (blog)](https://uhiyama-lab.com/en/notes/ue/motion-matching-game-animation-sample/); "combinatorial explosion … adding a new movement type requires new states, new transitions, and new blend trees" — [mocaponline (vendor blog)](https://mocaponline.com/blogs/mocap-news/motion-matching-games-guide); a common hybrid is motion matching for lower body/locomotion and state machines for upper-body abilities — [strayspark (blog)](https://www.strayspark.studio/blog/motion-matching-control-rig-ue5-animation)

### Inferences
- Inputs/outputs: input = predicted trajectory (positions/facings at e.g. −0.3…+1.0 s, from the movement model) + current pose history (foot/pelvis positions and velocities) + gameplay tags that select databases; output = (asset, time, mirror flag) fed into the Blend Stack, which inertially blends into it. Everything downstream (warping, steering, IK) is unchanged from the state-machine pipeline, which is why GASP keeps those layers.
- Motion matching trades authored structure for data coverage: no transition graph, but you need enough clips that the nearest neighbour is close. Epic's own note that "weights cannot fix poor coverage" and the use of warping to fill gaps is the key engineering admission. The per-frame search is throttled (`Search Throttle Time`) and biased to continue (`Continuing Pose Cost Bias`) to avoid jitter between near-equal candidates.

### Gaps
- No Epic page gives numeric CPU/memory costs or GASP's animation/database counts; Epic's Unreal Fest "Motion Matching in UE5" talk content was not retrieved.
- Chooser column types beyond bool and numeric range (enum, gameplay tag, random weight) are not on the page fetched.

## 5. Physics blending: Physical Animation Component, RigidBody node, AnimDynamics, Chaos ragdoll, hit reactions; physics-driven vs animation-driven

### Takeaway
UE has three tiers: AnimDynamics (cheap, collision-free box-and-constraint spring sim for secondary motion, inside the AnimGraph), RigidBody node (component-space Chaos sim of the physics asset, inside the AnimGraph, with clamps on how much world motion enters it), and the Physical Animation Component (motor drives on real physics bodies that pull them toward the animated target, blended per bone with the mesh's physics blend weight — the route to hit reactions and partial ragdoll).

### Cited Findings
- AnimDynamics: "light-weight physics simulation solution … physics-based, secondary animation"; simulates its own boxes, "Does not calculate collision. Constraints restrict movement instead"; `Bound Bone`, `Chain`/`Chain End` ("much more resource intensive"), `Box Extents`, Linear/Angular/Planar/Spherical limits, `Linear Spring`/`Angular Spring` with constants, gravity scale/override, `External Force` (world-space pin), damping overrides (default 0.7), `Angular Bias`, simulation space (Component/Actor/World/Root Relative/Bone Relative), `Component Linear Acc/Vel Scale` and `Applied Linear Acc Clamp`, wind, `Num Solver Iterations Pre/Post Update`; "Reset Dynamics" notify exists — [Epic docs, AnimDynamics](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-animdynamics-in-unreal-engine); [Epic docs, Animation Notifies](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-notifies-in-unreal-engine)
- RigidBody node: "lightweight physics simulation driven by the character's physics asset … more features than the Anim Dynamics node"; operates in Component Space; bodies set `Simulated` vs `Kinematic` (kinematic follow the animation); `Override Physics Asset`; `Simulation Space` = Component / World / Base Bone; `External Forces`; `Transfer Bone Velocities`; `Freeze Incoming Pose on Start` ("useful for ragdolls"); `Evaluation Rest Time`; `Reset Dynamics` after teleports; `Overlap Channel`; Sim Space Settings: `Master Alpha` (0 fully local … 1 world-like), `Velocity Scale Z`, `Max Linear Velocity`, `Max Angular Velocity` (~10 rad/s for fast-rotating characters), `Max Linear Acceleration` (a few hundred cm/s² typical), `Max Angular Acceleration` (~100), external drag/velocity for wind/podium effects; tuning advice: taper masses along the chain, damping ~5.0 — [Epic docs, Rigid Body](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-rigid-body-in-unreal-engine)
- Physical Animation Component API: `apply_physical_animation_settings(body_name, data)`, `…_below(body_name, data, include_self)`, `apply_physical_animation_profile_below(body_name, profile_name, include_self, clear_not_found)`, `get_body_target_transform(body_name)` ("the target transform for the given body"), `set_skeletal_mesh_component`, `set_strength_multiplyer` ("Multiplies the strength of any active motors, and can be blended from 0 to 1") — [Epic Python API, PhysicalAnimationComponent](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/PhysicalAnimationComponent)
- `PhysicalAnimationData` fields: `is_local_simulation` ("Whether the drive targets are in world space or local"), `orientation_strength` ("The strength used to correct orientation error"), `angular_velocity_strength`, `position_strength` ("Only used for non-local simulation"), `velocity_strength`, `max_linear_force`, `max_angular_force` ("The max force used to correct angular errors") — [Epic Python API, PhysicalAnimationData](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/PhysicalAnimationData)
- Community tuning notes: a high orientation strength (1000) made a mesh erratic; applying physical animation to the pelvis makes it aim for world-space orientation, so zero its strength (forum/answers, anecdotal) — [Epic forums](https://forums.unrealengine.com/t/physical-animation-component-rotates-skeletal-mesh/377517)
- Epic's own blog shows Lyra-era hit reactions use the physics route; (not retrieved — see Gaps)

### Inferences
- "Animation-driven physics" in UE = kinematic bodies or motor drives (Physical Animation) chasing the animated pose: the pose is the setpoint, physics adds compliance/impacts. "Physics-driven animation" = simulated bodies (RigidBody node, full ragdoll) whose result overwrites the pose. The per-body `physics blend weight` on the mesh, the `strength_multiplyer`, and the RigidBody `Master Alpha` are the three continuous dials for moving between them, and all are per-bone, so a character can be "animation above the hips, physics below" or vice versa.
- Hit reactions in UE are typically: apply a physical-animation profile below the hit bone, add an impulse, blend strength back to 0 over ~0.5–1 s — assembled from the API shape; no fetched page states the recipe verbatim.
- The clamp vocabulary (max linear/angular velocity and acceleration, external force pins, sim-space alpha) is directly translatable to a robot's "how much of the base motion do I let into the compliant layer."

### Gaps
- Epic's Physical Animation user-guide page returned an empty body; motor-profile UI, `Set All Bodies Below Simulate Physics`/`Physics Blend Weight` functions and Chaos ragdoll setup are not quoted from a primary source.
- No fetched page describes Lyra's hit-reaction implementation.

## 6. Procedural life: idle breaks, look-at, head/eye tracking, secondary motion, additive breathing, modifiers, curves driving procedural layers

### Takeaway
UE's "life" layer is mostly additive and curve-driven: mesh-space additive clips/aim offsets layered over the base pose, a Look At skeletal control for head/eye tracking, AnimDynamics/RigidBody for secondary motion, Pose Driver/Pose Blender for curve-driven correctives, and per-clip curves/metadata that modulate procedural nodes (IK alpha, warping, leans).

### Cited Findings
- Look At node: "Simple controller that make a bone to look at the point or another bone"; `bone_to_modify`, `look_at_target` (bone/socket; `look_at_location` is a world-space target if no bone, else an offset in that bone's space), `look_at_axis`, `look_up_axis`/`use_look_up_axis`, `look_at_clamp` (degrees; with Z axis only X/Y clamp used), `interpolation_type`/`interpolation_time`/`interpolation_trigger_threashold` (sic), `alpha` with bool/curve/scale-bias alpha inputs, `lod_threshold` — [Epic Python API, AnimNode_LookAt](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimNode_LookAt)
- Additive layers: `Apply Additive`/`Apply Mesh Space Additive` with alpha; aim offsets are mesh-space additive blend spaces; Lyra's FullBody Aiming layer receives the root yaw offset — [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine); [Epic docs, Blend Spaces](https://dev.epicgames.com/documentation/en-us/unreal-engine/blend-spaces-in-unreal-engine); [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)
- GASP's life-ish layers: `Simple Additive Lean` (BlendSpace driven by lateral acceleration via `GetLeanAmount`), `Simple Aim Offset` (turns toward camera when strafing, with Dead Blending), `Steering` — [Epic docs, Game Animation Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-animation-sample-project-in-unreal-engine)
- Curves "can drive arbitrary values, often IK alpha values"; curve types can drive morph targets and material parameters by name; metadata curves are constant per-clip flags — [Epic docs, Animation Curves](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-curves-in-unreal-engine)
- Pose assets (per-frame poses as curves, additive option) are driven at runtime by `Pose Blender` / `Pose Driver` — [Epic docs, Pose Assets](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-pose-assets-in-unreal-engine)
- Secondary motion: AnimDynamics (springs, chains, gravity, wind, external force) and RigidBody (ponytails, chains, hanging bones, collisions with level) — [Epic docs, AnimDynamics](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-animdynamics-in-unreal-engine); [Epic docs, Rigid Body](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-rigid-body-in-unreal-engine)
- Animation Modifiers generate curves/markers offline (foot-contact sync markers; Lyra's `Turn Yaw Anim Modifier` bakes root rotation into curves; Distance Curve Modifier) — [Epic docs, Animation Modifiers](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-modifiers-in-unreal-engine); [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine); [Epic docs, Distance Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/distance-matching-in-unreal-engine)
- Disney's robot character runs "An always-on periodic layer [that] handles eye blinks and antenna motion" as a background loop under triggered clips and joystick offsets — [Disney Research, Design and Control of a Bipedal Robotic Character (arXiv HTML)](https://arxiv.org/html/2501.05204v1)

### Inferences
- "Idle breaks" are not a node in UE; they are authored clips chosen by a state machine (random transition timer) or a Chooser/Blend Stack with random-weight rows, inertially blended, and they are the clearest example of animator intent (LIFE) riding on the same machinery as functional states. Breathing is normally an additive looping clip applied via `Apply Additive` with an alpha curve, so it survives under any base pose.
- Curves are the contract between animator and engineer: the animator keys `DisableLegIK`-style curves, foot-lock flags, lean amounts; the engineer's procedural nodes read them via `Get Curve Value`. For a robot this is the natural place to encode "how much may the controller deviate from this clip right now."

### Gaps
- No Epic page fetched documents a specific "idle break" or "breathing additive" recipe; the Lyra/GASP pages don't mention them. The Look At user guide (interpolation semantics) was empty; only API fields are cited.

## 7. Epic's recommended locomotion structure (Lyra: base layer + linked layers per weapon/gait via an Anim Layer Interface), known state-machine weaknesses, and the UAF future

### Takeaway
Epic's reference structure (Lyra) is a single base AnimBP (`AnimBP_Mannequin_Base`) that owns measurement and the locomotion state machine, with an Anim Layer Interface (`ALI_ItemAnimLayers`) exposing override points implemented by per-weapon child AnimBPs of `ABP_ItemAnimLayersBase`; GASP replaces the locomotion state machine with motion matching plus Choosers but keeps the same downstream layers. Epic's stated reason for motion matching is that state machines need hand-built transition and blending logic that does not scale with content; its next step is UAF (Unreal Animation Framework), still Experimental in 5.7/5.8.

### Cited Findings
- Lyra: `AnimBP_Mannequin_Base` builds the final pose; the system was "created almost entirely in Blueprints" and "inspired by Paragon and Fortnite, which … reach similar results through custom C++"; `ALI_ItemAnimLayers` "defines override points for locomotion states, aiming (including `FullBody_Aiming`), and skeletal controls"; `ABP_ItemAnimLayersBase` is the base linked layer all weapons use, children like `ABP_PistolAnimLayers` swap animations/variables; `Get Main Anim BPThreadSafe` lets layers read Acceleration/Velocity from the base via Property Access "avoiding recalculation"; layers choose clips in `On Become Relevant`; `LocomotionSM` has Idle/start/cycle/stop and a Jump path via the `JumpSources` alias; Gameplay Tag bindings map Gameplay Ability System events into the AnimBP; notify data is exposed to transitions for timing; debugging via Pose Watch Manager and Rewind Debugger — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine)
- Layer interfaces are for "high-complexity projects, such as live-service games where animations are often added or updated," and support multi-user work because logic is split across assets; Fortnite stacks a weapons interface and a vehicles interface — [Epic docs, Animation Blueprint Linking](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-linking-in-unreal-engine)
- Community description of the same pattern: the interface holds placeholders with no defined functions and layers are assigned at runtime — [Epic forums](https://forums.unrealengine.com/t/where-is-current-anim-layer-loaded-in-lyra/535663/4)
- GASP structure: `ABP_SandboxCharacter` with Motion Matching + Pose History in the AnimGraph; Event Graph sets variables; functions `SetReferences`, `UpdateEssentialValues`, `UpdateStates` (gameplay states as enums for Chooser filtering), `JustTraversed`, `ShouldTurnInPlace`, `ShouldSpinTransition`; layers: Motion Matching (with Orientation Warping + Steering in its Blend Stack Graph), Simple Additive Lean, Simple Aim Offset, Default Slot (traversal montages), Offset Root Bone, Leg IK, Orientation Warping — [Epic docs, Game Animation Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-animation-sample-project-in-unreal-engine)
- Epic on state machines vs motion matching: motion matching works "without the need to set up transition or blending logic between Animation Sequences" — [Epic docs, Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine); Epic's state-machine docs themselves offer Conduits and (Global) Aliases specifically to consolidate transitions — [Epic docs, State Machines](https://dev.epicgames.com/documentation/en-us/unreal-engine/state-machines-in-unreal-engine)
- UAF: Epic's 5.7 GASP post says sample content using UAF slipped from 5.7, "For 5.8, we plan to have a character in GASP set up entirely using UAF," and UAF "will remain Experimental in 5.8"; an Epic staff forum post calls UAF "highly experimental to the point where we are recommending not using it at the moment"; there is a `UAF` plugin index and an `FUAFBlendStack` type — [Epic tech blog (search snippet)](https://www.unrealengine.com/en-US/tech-blog/explore-the-updates-to-the-game-animation-sample-project-in-ue-5-7); [Epic forums](https://forums.unrealengine.com/t/mover-uaf-motionmatching/2698076); [Epic API, UAF plugin index](https://dev.epicgames.com/documentation/unreal-engine/API/PluginIndex/UAF?lang=en-US)

### Inferences
- The structural lesson is separation of concerns by data flow: measurement (velocity, acceleration, ground distance, yaw offset) is computed once, thread-safe, in the base; selection (which clip) is delegated to swappable layers or data tables (Chooser) keyed on gameplay state; shaping (warping, distance matching) and grounding (IK) are fixed post-process stages. Weapon/gait variants never touch the shaping or grounding code.
- The "spaghetti" weakness is visible in the docs' own remedies: priority-ordered rules, conduits, aliases, global aliases, `Max Transitions Per Frame`, transition interrupts. Each exists because N states need O(N²) hand-authored edges and the timing of each edge is a bespoke decision; motion matching collapses the edge set into one cost function, at the price of data coverage and CPU. The phrase "spaghetti transitions" itself is not in any fetched Epic page.

### Gaps
- No Epic primary source was found that states the state-machine scaling problem in Epic's own words; only the Motion Matching page's "without the need to set up transition or blending logic" and community blogs.
- What UAF changes architecturally (graph model, threading) is not described on any page fetched.

## 8. Public examples of UE animation concepts applied to real robots

### Takeaway
I found no public, primary-source example of a physical robot whose body is driven by Unreal Engine's animation runtime. The closest documented cases are Disney Research's bipedal character (animator-authored clips, a layered "animation engine" with blends, and RL policies that imitate them — the same layering as a game pipeline, implemented without Unreal), Disney Imagineering's animatronic workflow (animate a virtual rig, flag physical limits, transfer to motors) and Disney attractions rendering in Unreal. Claims about Engineered Arts/Unitree/Boston Dynamics using Unreal animation could not be substantiated.

### Cited Findings
- Disney Research "Design and Control of a Bipedal Robotic Character" (2025): four-stage pipeline — animation, mechatronic design, reinforcement learning, run-time tools; "Animators defined the character's motion style, creating both periodic motions (like walking) and episodic motions"; at run time "command signals are generated by an animation engine which composes and blends between multiple animation sources" — [Disney Research publication page](https://la.disneyresearch.com/publication/design-and-control-of-a-bipedal-robotic-character/); [arXiv PDF](https://arxiv.org/pdf/2501.05204)
- Run-time details: sources are Maya-authored episodic clips (each paired with an imitation policy), a procedural gait built from walk-cycle samples at several speeds (via MPC + inverse dynamics into whole-body references), an always-on background loop (eye blinks, antenna), remote-triggered clips, and a two-joystick gamepad; triggered layers ramp in/out over 0.1 s (show functions) or 0.35 s (body), positions/joint angles lerp and orientation slerps; policy inputs are command tuples (head/torso offsets, 2D path velocity, turn rate, phase harmonics), body-frame velocities, joint positions/velocities and previous actions; policies output joint setpoints at 50 Hz, low-passed at 37.5 Hz onto a 600 Hz PD actuator bus; walk-to-stand switches wait for the next double-support phase; limitations: one policy per episodic motion, walking tops out at 0.7 m/s, ~10 h of public runtime with no falls; "No Unreal, Unity, blend trees, or explicit state machines are mentioned" — [arXiv HTML](https://arxiv.org/html/2501.05204v1)
- Press: the child-sized robot's "five-degree-of-freedom legs and hips allow it to balance and waddle … and even catch itself when given a playful shove" — [Popular Science](https://www.popsci.com/technology/disney-robot-cute-animation/)
- Disney animatronics workflow (Lumiere): motion "first choreographed digitally on the computer with a virtual rig," software flags the robot's physical limits, animator adjusts, then the performance is transferred to the audio-animatronic's motors — [Disney Animation, Pixels to Parks writeup (PDF)](https://media.disneyanimation.com/uploads/production/publication_asset/99/asset/LumiereWriteup.pdf)
- A Disney attraction "renders in real time and uses the UNREAL engine" (recap of a Disney R&D presentation; rendering, not robot control) — [Laughing Place](https://www.laughingplace.com/disney-parks/we-call-it-imagineering-r-d-recap)
- Unitree G1 co-speech gesture pipeline deploys synthesized gestures in real time via an imitation-learning balance policy; no Unreal involvement — [arXiv 2512.17183](https://arxiv.org/html/2512.17183v1)
- Unreal's Live Link streams external animation data onto in-engine actors via Live Link controllers; no page describes an outbound bridge to servos — [Epic docs, Using Live Link data](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-live-link-data-in-unreal-engine)

### Inferences
- The Disney biped is the best existence proof for the layered idea on hardware: authored clips → layered blend/ramp "animation engine" → per-skill RL tracking policies → PD actuators. It mirrors UE's "pose source → blend → adaptation" layering with the adaptation layer replaced by learned policies rather than IK/warping. Its stated bottleneck (one policy per clip) is exactly where a UE-style runtime (one clip-agnostic tracker + warping/IK) would differ.
- Nothing found suggests anyone runs UE's AnimGraph in the loop of a walking robot; using UE as an authoring/retargeting front end (Blender/Maya-like) with export to a robot runtime is the realistic pattern.

### Gaps
- No sources found for Engineered Arts (Ameca), Boston Dynamics or Unitree using Unreal's animation system; the search returned only MetaHuman/Live Link marketing and a simulation student project.

## 9. Mechanism map: layer, LIFE vs ADAPTABILITY, inputs → outputs (my classification; mechanism facts cited in sections 1–6)

### Takeaway
Read top-to-bottom as the per-frame stack. "L" = mainly life/character (animator intent), "A" = mainly realism/adaptability (environment, physics, responsiveness), "L/A" = both.

### Cited Findings
- The ordering and node names below come from Lyra and GASP as documented — [Epic docs, Animation in Lyra](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-in-lyra-sample-game-in-unreal-engine); [Epic docs, Game Animation Sample](https://dev.epicgames.com/documentation/en-us/unreal-engine/game-animation-sample-project-in-unreal-engine)

### Inferences
| Layer | Mechanism | L/A | Inputs | Outputs |
|---|---|---|---|---|
| 0 Measurement | EventGraph / ThreadSafeUpdate, Property Access | A | velocity, acceleration, ground distance, controller yaw, gameplay tags | floats/enums for the graph |
| 1 Clip source | Sequence Player, Blend Space 1D/2D (speed, direction), Sync Groups/Markers | L (clips) / A (axis inputs, phase sync) | axis values, play rate, sync markers | pose + curves + root-motion delta; leader phase |
| 1 Selector | State Machine + Transition Rules; or Motion Matching + Chooser; Blend Stack | L (authored structure) / A (MM: trajectory-driven) | bools/times/notifies; or trajectory + pose history + tags | which (clip, time), blend request |
| 2 Timing | Distance Matching, play-rate matching | A | predicted stop/pivot distance, ground distance | explicit clip time / play rate |

## 10. Lessons for a layered robot controller

### Takeaway
Borrow the stack, not the engine: authored clips with curves and markers as the "intent" source; a thin selector; one continuity post-process; explicit shaping and grounding stages with alphas; a physics/compliance layer whose contribution is clamped; events on the clip timeline.

### Cited Findings
- Epic's inertialization rules of thumb: blend < ~0.4 s, avoid when poses differ greatly; Dead Blending's velocity caps (500 cm/s, 360 deg/s) — [Epic docs, Transition Rules](https://dev.epicgames.com/documentation/en-us/unreal-engine/transition-rules-in-unreal-engine); [Epic docs, Blend Nodes](https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-blueprint-blend-nodes-in-unreal-engine)
- Disney's ramps (0.35 s body, 0.1 s show functions), 50 Hz policy setpoints filtered at 37.5 Hz onto a 600 Hz PD bus, and switching gaits only at double support — [arXiv HTML](https://arxiv.org/html/2501.05204v1)

### Inferences
- Keep one pose stream and put a single inertializer after the selector; any switch (clip, layer, gesture) becomes a blend request with a duration, not bespoke blend code. Store last pose + velocity; decay the offset; clamp the decay velocity at actuator limits.
- Make clips carry metadata the controller reads: foot-contact markers (sync + foot lock), a distance curve (for start/stop retiming), per-clip "allow-IK/allow-warp alpha" curves, and metadata flags. That is the animator↔controller contract in UE and it needs no engine.
- Separate "selection" from "shaping": gait/speed/heading mismatch is fixed by stride/orientation warping and distance matching on the IK foot targets before the leg solver, never by picking a different clip. Only then solve IK to the real floor, and drop the pelvis rather than over-extend (UE's `Pull Pelvis Down`, `Clamp IK Using FK Limits`, `soft_percent_length`).
- Layer by body region with per-bone weights (Layered blend per bone / blend masks): upper-body gestures over lower-body locomotion, with a mesh-space rotation blend so the head stays where the animator pointed it.
- Treat physics as a filter with dials, not a mode: a strength multiplier 0…1 per body and velocity/acceleration clamps on how much base motion enters the compliant layer, so "hit reaction" = raise compliance below the hit joint for 0.5 s, then blend back.
- Sync by phase, not by time: with marker-based sync a follower clip is re-timed to the leader's foot-contact markers; the same mechanism lets a robot blend walk variants without crossing feet. Switch gaits at a contact phase (Disney waits for double support).
- Fire discrete events off the clip timeline with a weight threshold and leader-only rules, so sounds/LED/servo "show functions" never double-fire during blends.
- Expect motion matching to pay off only with dense clip coverage; for a small clip library a state machine with aliases and a cost-biased Blend Stack is cheaper and more predictable.
- Do not expect to run UE in the loop on the robot; use it (or Blender) for authoring, retargeting (IK Rig/Retargeter) and previewing limits, and port the runtime ideas.

### Gaps
- No source quantifies how these layers degrade on a low-DOF biped; the robot-side numbers above are Disney's and should be re-measured on the target hardware.
