# Unity character animation architecture (as of 2026), read for a small physical biped

Scope: Unity's built-in Mecanim stack, the Animation Rigging package, the Playables / Animation C# Jobs layer, the code-driven replacements (Animancer), motion matching (Kinematica, MxM, newer packages), the physics/IK middleware professionals actually buy (Final IK, PuppetMaster), ArticulationBody and ML-Agents, procedural "life" techniques, Unity's own locomotion template, and the few public cases of Unity animation driving real hardware. Each mechanism is tagged LIFE (personality, animator intent) or REALISM (fitting environment/physics, responsiveness); those tags are my interpretation and live under "Inferences". Everything under "Cited Findings" is from the fetched source.

Research date: 2026-11-05. Unity docs fetched were the "current" (6000.6) and 2022.3 manuals; package versions: Animation Rigging 1.3.1, Timeline 1.8.13, Kinematica 0.8.0-preview (last), Animancer v8.4.

## Q0. How the mechanisms stack: frame order and the LIFE vs REALISM map

### Takeaway
Unity is a pipeline, not a monolith: clips are sampled into a pose by a graph (Animator Controller or a hand-built PlayableGraph), layers composite that pose by mask/weight (Override or Additive), root motion is extracted as a delta, then post-processes run in a documented order: built-in IK pass (OnAnimatorIK), Animation Rigging constraints (after the Animator's "normal evaluation"), then third-party LateUpdate solvers (Final IK), then physics mapping (PuppetMaster). Each later stage takes the previous pose as input and owns a weight that can fade it in or out.

### Cited Findings
- Animation Rigging "works on top of Unity's animation system, and so requires an Animator"; the Rig Builder "builds a Playable Graph that is added to the Animator's state machine" and its constraint jobs run "after its normal evaluation" of the Animator's pose. — [Rigging Workflow](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/RiggingWorkflow.html)
- Override layers replace "the animation on previous layers"; Additive layers "add the animation on this layer on top of the animation from previous layers". — [Animation Layers](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-layers)
- With masks, "The higher layers take precedence for the body parts they control." — [Avatar Mask](https://docs.unity3d.com/2022.3/Documentation/Manual/class-AvatarMask.html)
- Full Body Biped IK "runs each frame in LateUpdate, after the animation system has finished"; it reads the animated pose, maps it to a low-res solver rig, solves, maps back. — [Final IK FBBIK](http://www.root-motion.com/finalikdox/html/page8.html)
- PuppetMaster: each frame it reads the animated Target pose and passes it to the Puppet's muscles; after physics solves, the Target is mapped back to the Puppet's pose "based on the mapping settings" until animation overwrites it next frame. — [PuppetMaster Overview](http://www.root-motion.com/puppetmasterdox/html/page3.html)
- In Animation C# Jobs, `ProcessRootMotion` "handles the root transform motion, it is always called before ProcessAnimation". — [Animation C# Jobs blog](https://unity.com/blog/engine-platform/animation-c-jobs)
- Animator Update Mode: Normal = "updated in-sync with the Update call"; Animate Physics = "in-sync with the FixedUpdate call (i.e. in lock-step with the physics system)", recommended for characters that push Rigidbodies; Unscaled Time ignores timescale. — [Animator component](https://docs.unity3d.com/2022.3/Documentation/Manual/class-Animator.html)
- The Execution Order page lists `OnAnimatorMove` and `OnAnimatorIK` as "animation loop callbacks" and `OnStateMachineEnter/Exit`, `OnStateEnter/Update/Exit`, `OnStateMove`, `OnStateIK` for StateMachineBehaviours, but gives their placement only in a flowchart image; other animation functions "are internal to the animation system". — [Execution Order](https://docs.unity3d.com/2022.3/Documentation/Manual/ExecutionOrder.html)

### Inferences
Documented order of a frame, bottom to top (my synthesis of the citations above):

| Stage | Mechanism | Inputs | Outputs | Mainly brings |
|---|---|---|---|---|
| 1 | Parameters (float/int/bool/trigger) set by gameplay code, or by curves in clips | sensors, input, timers | numbers the graph reads | neither; it is the interface |
| 2 | State machine + transitions (Animator Controller) or code-driven state selection (Animancer, Playables) | parameters, exit times | which clips play, crossfade weights | LIFE (which authored motion plays) |
| 3 | Blend trees (1D, 2D directional/cartesian, Direct) | 1-2 floats (speed, turn) or per-child weights | weighted pose from several clips | LIFE with a REALISM hook (continuous response to speed/turn) |
| 4 | Layer compositing (Override/Additive, Avatar Mask, layer weight, Sync) | per-layer poses | one composite pose | LIFE (upper-body gestures, additive breathing on top of locomotion) |
| 5 | Root motion extraction (body transform -> root transform delta; OnAnimatorMove) | composite pose's root curves | deltaPosition/deltaRotation applied to the object | REALISM (feet do not slide; motion matches clip) |
| 6 | Built-in IK pass (OnAnimatorIK: hands/feet goals, look-at, humanoid only) | goal positions, weights | corrected limb/head pose | REALISM (contact, look-at targets) |
| 7 | Animation Rigging constraints (TwoBoneIK, MultiAim, Damped, MultiParent, Override, ChainIK, Twist) | targets/sources, per-constraint weights | post-processed pose | REALISM for IK/aim; LIFE for damped/secondary |
| 8 | Third-party LateUpdate solvers (Final IK FBBIK, Grounder, LookAtIK, AimIK, VRIK) | targets, raycasts, weights | pose with ground contact and full-body reach | REALISM |
| 9 | Physics mapping (PuppetMaster muscles/pins; ArticulationBody drives) | kinematic target pose | dynamic pose that obeys collisions | REALISM (plus LIFE if "wobble" is wanted) |
| 10 | Motion matching replaces stages 2-3 (and often 4) with a per-frame database search driven by a predicted trajectory | current pose + desired trajectory | clip/frame to play, inertialized blend | REALISM (responsiveness) while preserving mocap LIFE |

- The ordering of stage 6 relative to stage 7 is not explicitly documented; the Rigging docs say constraints run after the Animator's evaluation, and the IK pass is part of the Animator's layer evaluation (IK Pass is a per-layer flag), so I infer built-in IK runs before Rigging constraints.

### Gaps
- Unity does not publish the exact internal order of layer evaluation beyond "previous layers" semantics; no document found states that the base layer weight is fixed at 1 (I believe it is, but could not cite it).
- No document found gives the blend-weight formula for 2D Freeform blends (only the "influence field" description).

## Q1. Mecanim: Animator Controller, transitions, blend trees, layers, parameters, root motion, rigs, IK, final pose

### Takeaway
Mecanim is a data-driven asset (Animator Controller) interpreted by the Animator component: states hold clips or blend trees, transitions fire on parameter conditions and/or normalized exit time with explicit interruption rules, layers composite poses by mask and Override/Additive mode, root motion is extracted from a "body transform" projected to a "root transform", and a humanoid Avatar converts bone rotations into a rig-independent "muscle" pose that enables retargeting and a built-in IK pass.

### Cited Findings

States and sub-state machines
- State properties: Motion ("The animation clip or blend tree assigned to this state"), Speed ("The default speed of the motion", with a Parameter option), Motion Time ("The time used to play the motion for this state", parameter-drivable), Mirror ("Enable to mirror the animation for this state", humanoid only), Cycle Offset ("The offset added to the state time of the motion. This offset does not affect the Motion Time", parameter-drivable), Foot IK ("Enable to respect Foot IK for this state", humanoid only), Write Defaults ("Whether the AnimatorStates writes the default values for properties that are not animated by its motion"). — [Animation State](https://docs.unity3d.com/2022.3/Documentation/Manual/class-State.html)
- Sub-state machines "collapse a group of states into a single named item"; the grouping is only visual, so a transition into one must pick a concrete target state; each contains an "Up" state representing "the 'outside world'"; they can nest. — [Sub-State Machines](https://docs.unity3d.com/2022.3/Documentation/Manual/NestedStateMachines.html)
- StateMachineBehaviours attach "to an individual state within a state machine" and run "when the state machine enters, exits or remains within a particular state", with events for root motion and IK; suggested uses include "Perform certain tests (eg, ground detection) only when in appropriate states". — [StateMachineBehaviours](https://docs.unity3d.com/2022.3/Documentation/Manual/StateMachineBehaviours.html)

Transitions
- Exit Time is "represented in normalized time (for example, an exit time of 0.75 means that on the first frame where 75% of the animation has played, the Exit Time condition is true). On the next frame, the condition is false." Exit times < 1 "are evaluated every loop"; > 1 "are evaluated only once". — [Transitions](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/class-transition)
- Fixed Duration: checked, "the transition time is interpreted in seconds"; unchecked, "as a fraction of the normalized time of the source state". Transition Offset: "a value of 0.5 means the target state begins playing at 50% of the way through its own timeline". — same source
- Interruption Source values: None ("Don't add any more transitions"), Current State, Next State, Current State then Next State, Next State then Current State; "Transitions from AnyState are always queued first"; Ordered Interruption checked stops parsing when "A valid transition or the current transition has been found", unchecked when "A valid transition has been found". "Only an [AnyState] transition can be interrupted by itself." — same source
- Conditions: "If your transition has no conditions, the Unity Editor only considers the Exit Time"; with conditions and Has Exit Time, "Unity only checks these conditions after the exit time of the state". "You can only activate one transition at a given time." — same source
- The transition graph shows a white line of IK foot contact ("When the white line is at the top of the graph, the Left foot contacts the floor plane") to help align footfalls; a "smooth transition avoids foot slips, jumps in animation, and preserves the dynamics of the motion". — same source

Blend trees
- Blend Trees are "a special type of state"; blended motions "must be of similar nature and timing", aligned in normalized time ("the left foot hits at 0.0 and the right foot at 0.5"); "Since normalized time is used, it doesn't matter if the clips are of different length." — [Blend Trees](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-blend-trees/class-blend-tree)
- 1D: at a threshold "its animation weight is 1 and the other animations have a weight of 0"; Automate Thresholds spreads evenly; Compute Thresholds can set thresholds from root-motion Speed, Velocity X/Y/Z, Angular Speed (Rad/Deg); example walk 1.5, jog 2.3, run 4 units/s, parameter 3.0 "would blend the jog and run with a slight bias toward the jog". — [1D Blending](https://docs.unity3d.com/2022.3/Documentation/Manual/BlendTree-1DBlending.html)
- 2D Simple Directional: for "walk forward", "walk backward", "walk left", "walk right"; optional single motion at (0,0); avoid two motions in the same direction. 2D Freeform Directional: multiple motions may share a direction (walk and run forward) and "the set of motions should always include a single motion at position (0, 0), such as 'idle'". 2D Freeform Cartesian: for motions that "do not represent different directions", e.g. X = angular speed, Y = linear speed. Weights are described as influence fields (full influence at the motion's own position, decreasing with distance); no formula given. Compute Positions offers Velocity XZ and Speed And Angular Speed. — [2D Blending](https://docs.unity3d.com/2022.3/Documentation/Manual/BlendTree-2DBlending.html)
- Direct: "map animator parameters directly to the weight of a BlendTree child"; "bypasses the crossfading, or the various 2D blending algorithms"; "particularly useful when mixing blend shape animations for facial expressions" and "when blending together additive animations". — [Direct Blending](https://docs.unity3d.com/2022.3/Documentation/Manual/BlendTree-DirectBlending.html)

Layers, masks, sync
- Layers exist "for managing complex state machines for different body parts" ("a lower-body layer for walking-jumping, and an upper-body layer for throwing objects / shooting"). The Mask "specifies the body parts on which to apply the animation". "For additive blending to be successful, the animation on the additive layer must contain the same properties as the previous layers." — [Animation Layers](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-layers)
- Sync: a synced layer "is an instance of the source of the synced layer"; "The only changes that are unique to the synced layer are the selected animations used within each state" (example: a Fatigued layer with swapped clips). Timing unselected: synced-layer clips are stretched to the original layer's length ("the original layer is the sole master"); selected: length is "a balance for both animations, based on weight". — same source
- Humanoid Avatar Mask body parts: Head, Left/Right Arm, Left/Right Hand, Left/Right Leg, Root; IK toggles for hands and feet determine "whether or not to include IK curves in animation blending"; for generic rigs a Transform mask is used (Import Skeleton, tick bones). Masks also cut cost: unused curves "don't have to be computed during playback". — [Avatar Mask](https://docs.unity3d.com/2022.3/Documentation/Manual/class-AvatarMask.html)
- `Animator.SetLayerWeight(int layerIndex, float weight)`: "Sets the weight of the layer at the given index." — [SetLayerWeight](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Animator.SetLayerWeight.html)

Parameters, events, curves
- Four parameter types: Integer, Float, Bool, Trigger ("a boolean parameter that is reset by the controller when consumed by a transition"); set via `SetFloat`, `SetInteger`, `SetBool`, `SetTrigger`, `ResetTrigger`; "the value of a parameter can be updated by an animation curve" and read back by script (example: varying a sound's pitch). — [Animation Parameters](https://docs.unity3d.com/2022.3/Documentation/Manual/AnimationParameters.html)
- Animation Events call a function on the GameObject at a clip time; the method must "only accept a single parameter of type float, int, string, an object reference, or an AnimationEvent object"; typical use is footstep sounds. — [Animation Events](https://docs.unity3d.com/2022.3/Documentation/Manual/script-AnimationWindowEvent.html)

Root motion
- "The Body Transform is the mass center of the character. It is used in Mecanim's retargeting engine and provides the most stable displacement model." Body position/orientation "are the only world-space curves stored in the Animation Clip. Everything else: muscle curves and IK goals (Hands and Feet) are stored relative to the body transform." — [Root Motion](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/avatar-creationand-setup/root-motion)
- "The Root Transform is a projection on the Y plane of the Body Transform and is computed at runtime. At every frame, a change in the Root Transform is computed. This change in transform is then applied to the Game Object to make it move." Bake Into Pose per Rotation / Position Y / Position XZ keeps that component on the body instead; XZ baking "will usually be used for 'Idles'... It will stop the accumulation of small deltas drifting"; Position Y "Based Upon: Feet" makes "the Root Transform Position Y ... match the lowest foot Y for all frames ... which prevents floating problem when blending or transitioning". — same source
- Generic rigs: "instead of using the Body Transform to compute/project a Root Transform, the transform set in Root Node is used." Baking Y sets `Animator.gravityWeight` to 1 so "physics handles y-axis movement" (needs Character Controller or Rigidbody). — same source
- Animator component "Apply Root Motion: Select whether to control the character's position and rotation from the animation itself or from script." — [Animator component](https://docs.unity3d.com/2022.3/Documentation/Manual/class-Animator.html)
- Implementing `OnAnimatorMove` makes the Animator "show the Apply Root Motion property as Handled by Script"; the tutorial drives in-place running from a clip curve "Runspeed" read via `animator.GetFloat("Runspeed") * Time.deltaTime`. — [Scripting Root Motion](https://docs.unity3d.com/2022.3/Documentation/Manual/ScriptingRootMotion.html)

Humanoid vs Generic, Avatar, muscle space
- Humanoid needs "at least 15 bones organized in a way that loosely conforms to an actual human skeleton"; mapping shows green/red fit; strategy: Clear, Sample Bind-pose, Automap, Enforce T-Pose; the T-pose is "the default pose required by Unity animation". — [Configuring the Avatar](https://docs.unity3d.com/2022.3/Documentation/Manual/ConfiguringtheAvatar.html)
- "Unity's animation system allows you to control the range of motion of different bones using Muscles"; per-muscle ranges (default Head-Nod/Head-Tilt -40 to 40 degrees) can be narrowed "to add stiffness"; Translate DoF is off by default ("Unity animates the bones using only rotations") and "can increase performance requirements". — [Muscle definitions](https://docs.unity3d.com/2022.3/Documentation/Manual/MuscleDefinitions.html)
- `HumanPose` is a "Retargetable humanoid pose" that is "completely abstracted from any skeleton rig" with fields `bodyPosition`, `bodyRotation`, `muscles`; `HumanPoseHandler` lets you "create, read, and write the HumanPose for a humanoid avatar skeleton hierarchy". — [HumanPose](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/HumanPose.html), [HumanPoseHandler](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/HumanPoseHandler.html)
- Retargeting is "One of the most powerful features of Mecanim"; it needs a configured Avatar for "a correspondence between the models' bone structure"; recommended hierarchy is a top-level GameObject (Character Controller, scripts) with the model and Animator as a child, found via `GetComponentInChildren<Animator>()`. — [Retargeting](https://docs.unity3d.com/2022.3/Documentation/Manual/Retargeting.html)

IK pass
- Built-in IK "is supported in Mecanim for a humanoid character with a correctly configured Avatar"; enable IK Pass on a layer ("When enabled, IK Pass sends an OnAnimatorIK callback"); API: `SetIKPositionWeight`, `SetIKRotationWeight`, `SetIKPosition`, `SetIKRotation`, `SetLookAtPosition`, `SetLookAtWeight`, `bodyPosition`, `bodyRotation`; the sample sets `AvatarIKGoal.RightHand` and look-at inside `OnAnimatorIK`. — [Inverse Kinematics](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/avatar-creationand-setup/inverse-kinematics)
- `AvatarIKGoal` has exactly four values: LeftFoot, RightFoot, LeftHand, RightHand. — [AvatarIKGoal](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/AvatarIKGoal.html)

Known failure modes (community-documented)
- Write Defaults: mixing on/off across layers "causes tons of undocumented unity bugs"; with WD on, a transition into a blend tree can snap instead of blend when a parameter is animated. — [VRCFury WD write-up](https://vrcfury.com/technical/wd)
- Default values are captured when the GameObject activates, so pooled objects come back with stale values; workaround was crossfade to a WD-on state, `Update(0)`, then disable. — [Unity Discussions](https://discussions.unity.com/t/impossible-to-maintain-animator-default-values-in-all-scenarios/622123)
- An empty Override-layer state with WD on leaves lower layers alone, while WD off writes the default pose over them, which a user called "backwards". — [Unity forum thread 755174](https://forum.unity.com/threads/write-defaults.755174/)

### Inferences
- The final pose per frame is: for each layer in index order, evaluate its state machine (crossfades are weighted sums of clip poses; blend trees are weighted sums of children), then composite by mask: Override replaces masked bones proportionally to layer weight, Additive adds the layer's delta-from-reference proportionally to weight. This is consistent with the "previous layers" wording and the AnimationLayerMixerPlayable API (`SetLayerAdditive`, `SetLayerMaskFromAvatarMask`), which is the primitive Unity exposes for the same operation.
- Muscle space is the robot-relevant abstraction: a pose becomes a vector of normalized joint values plus a body (COM) transform, so any skeleton with the same joint semantics can play it. For a non-human biped with a Generic rig, muscle space is unavailable; the equivalent would be a hand-defined joint-space vector with per-joint ranges (the "muscle range" sliders are literally joint limits).
- "Foot IK" on a state plus the stored IK-goal curves is how Unity stops foot sliding under retargeting; a robot would get the same effect by storing foot-contact targets alongside joint trajectories.
- Root motion's "body transform = mass center; root = its ground projection" is the same split a robot controller needs: COM trajectory as the authored intent, with the ground-plane delta as the velocity command.
- LIFE vs REALISM: states/transitions/blend trees/layers/events/Cycle Offset/Mirror are LIFE tools (they decide which authored motion plays and how it is decorated); root motion, Foot IK, IK pass, Avatar muscle limits, Animate Physics update mode are REALISM tools.

### Gaps
- The muscle value range (I believe normalized -1..1 around the muscle's range) is not stated on the fetched HumanPose/muscle pages.
- Additional Settings (Arm Twist, Leg Twist, Arm/Leg Stretch, Feet Spacing) are listed on the muscle page but not described there.
- No fetched page lists `SetIKHintPosition` / `AvatarIKHint`, though it exists in the API.

## Q2. Animation Rigging package (com.unity.animation.rigging 1.3.1)

### Takeaway
Animation Rigging is a constraint stack that post-processes the Animator's pose inside the same PlayableGraph, using Animation C# Jobs; a Rig Builder on the Animator object owns ordered Rig layers, each a hierarchy of weighted constraints (TwoBoneIK, MultiAim, MultiParent, ChainIK, Damped Transform, Override Transform, Twist), evaluated in depth-first hierarchy order after the Animator's normal evaluation.

### Cited Findings
- Package 1.3.1 works with Unity "2023.2 and later"; purpose: "sets of constraints for adding procedural motion to animated objects"; example rig types: deformation rigs ("secondary motion to items like armor, props, and accessories") and World Interaction rigs that "combine IK and Aim constraints for targeting". — [Animation Rigging index](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/index.html)
- "The constraints in the Animation Rigging package are based on the C# Animation Jobs API." Twelve constraints: Blend, Chain IK, Damped Transform, Multi-Aim, Multi-Parent, Multi-Position, Multi-Referential, Multi-Rotation, Override Transform, Twist Chain, Twist Correction, Two Bone IK. — [Constraint Components](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/ConstraintComponents.html)
- Rig Builder sits on the Animator's GameObject, "builds a Playable Graph that is added to the Animator's state machine"; its layers "let you stack several Rigs and toggle each one"; "The Rig component gathers constraints using GetComponentsInChildren" (depth-first), producing an ordered job list that runs "after its normal evaluation"; "grouping constraints under a GameObject allows you to manage the evaluation order"; "The root of a control rig hierarchy should be at the same level as the skeleton root"; "Rig components, like all Constraint components, have a Weight property that can be used, animated, and scripted". — [Rigging Workflow](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/RiggingWorkflow.html)
- Two Bone IK: Root/Mid/Tip chain, Target ("desired position of the Tip"), optional Hint ("the direction the limb should be oriented when it bends"), Target Position Weight ("Root and Mid objects will extend as far as necessary"), Target Rotation Weight, Hint Weight, Maintain Target Offset; "Auto Setup from Tip Transform" creates Target/Hint. — [Two Bone IK](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/TwoBoneIKConstraint.html)
- Multi-Aim: Aim Axis, Up Axis, World Up Type (None/Scene Up/Object Up/Object Up Rotation/Vector), weighted Source Objects; it "calculates an aim rotation to each target, and then produces a weighted sum of all these rotations" (weights not normalized); Constrained Axes and Min/Max Limit clamp rotation. — [Multi-Aim](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/MultiAimConstraint.html)
- Damped Transform: "allows damping the position and rotation transform values from the source GameObject to the constrained GameObject"; Damp Position/Rotation 0 = follows directly, 1 = fully damped; Maintain Aim "forces the constrained object to always aim at the source object". — [Damped Transform](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/DampedTransform.html)
- Chain IK uses FABRIK; Root, Tip (descendant of Root), Target, Chain Rotation Weight, Tip Rotation Weight, Max Iterations, Tolerance ("finish ... if the distance is less than this value"). — [Chain IK](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/ChainIKConstraint.html)
- Override Transform: Override Source or explicit Override Position/Rotation, Space World/Local/Pivot (Pivot: displacement "added to" local values), Position/Rotation Weight; reference is "the initial position of the Override Source GameObject at the time the constraint is created". — [Override Transform](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/OverrideTransform.html)
- Multi-Parent: "moves and rotates a GameObject as if it is the child of another GameObject" without reparenting, multiple weighted sources, "does not affect scale", Constrained Position/Rotation Axes, Maintain Offset. — [Multi-Parent](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/constraints/MultiParentConstraint.html)
- History: preview for 2019.1, keyframing + effectors in 2019.2, multi-track authoring in 2019.3 (Unite Copenhagen 2019, Dave Hunt); the companion talk groups constraints as "world interaction, procedural secondary animation, and skeletal deformation fix-up" and names Jiggle Chain and Twist Chain. — [Unite Copenhagen 2019 slides](https://www.slideshare.net/unity3d/introducing-animation-rigging-for-unity-20193-unite-copenhagen-2019), [Extending with C# slides](https://www.slideshare.net/unity3d/extending-the-animation-rigging-package-with-c-unite-copenhagen-2019)
- SIGGRAPH 2019 workshop repo: the package "enables users to setup rigs to procedurally control skeletal animations as a post-process". — [animation-rigging-workshop-siggraph2019](https://github.com/unity-technologies/animation-rigging-workshop-siggraph2019)
- Community sample: head and spine turn to follow a movable target (built on 0.2.6 preview). — [animation-rigging-character-looking-around](https://github.com/SpiccyMayonnaise/animation-rigging-character-looking-around)

### Inferences
- Typical mapping for a biped: TwoBoneIK on each leg with Target = ground-probe point (foot placement) and on each arm (weapon/prop hands), MultiAim on head/neck/eyes (look-at), MultiParent for a held prop, Damped Transform on tail/antenna/ears (secondary motion), Override Transform for a joystick-style additive offset on torso/head. Weight per constraint and per Rig layer is the blend knob, so "how much realism to apply" is a float.
- LIFE vs REALISM: TwoBoneIK/ChainIK/MultiAim/MultiParent = REALISM (fit the environment); Damped Transform/Twist/Jiggle = LIFE (secondary motion, follow-through); Override Transform = either (it is the generic "add an offset" hook).
- Because the Rig is "a post-process" inside the same graph, the Animator never knows the constraints exist; the robot equivalent is a pure function pose_in -> pose_out that is parameterized by weights and targets.

### Gaps
- The constraint pages do not describe how the solver handles unreachable targets beyond "extend as far as necessary".
- The workshop PDF content (constraint-to-body-part recipes, custom IAnimationJob code) could not be read from the repo page.

## Q3. Playables API, Animation C# Jobs, Animancer and the "state machine spaghetti" problem

### Takeaway
Playables is the engine primitive beneath both Animator Controllers and Timeline: a PlayableGraph of nodes (AnimationClipPlayable, AnimationMixerPlayable, AnimationLayerMixerPlayable, AnimatorControllerPlayable, AnimationScriptPlayable) feeding an AnimationPlayableOutput bound to an Animator. Animancer wraps this so gameplay code plays clips directly, citing six Mecanim problems (setup overhead, opacity, one-controller coupling, magic strings, undocumented dependencies, ignored/delayed commands).

### Cited Findings
- Playables "complement the Mecanim animation system"; you can "Play an animation clip without having to create and manage an Animator Controller asset", "Dynamically create blend graphs and control blend weights", and "Dynamically add or adjust playable nodes at runtime instead of creating a complex static graph that accounts for all possible outcomes". The Playable Director "is primarily used by the Unity Timeline package". — [Playables API](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/playables)
- "A playable is a C# struct that implements the IPlayable interface" (structs to avoid GC); "The PlayableGraph is responsible for the life cycle of its playables and their outputs"; `PlayableOutput.SetSourcePlayable()` links the root; `PlayableGraph.Create/Play/Stop/Evaluate/Destroy`, and "You must manually call this destroy method to destroy a PlayableGraph". — [PlayableGraph](https://docs.unity3d.com/2022.3/Documentation/Manual/Playables-Graph.html)
- Examples: `mixerPlayable = AnimationMixerPlayable.Create(playableGraph, 2);` `playableGraph.Connect(clipPlayable0, 0, mixerPlayable, 0);` `mixerPlayable.SetInputWeight(0, 1.0f-weight);` `mixerPlayable.SetInputWeight(1, weight);`; an `AnimatorControllerPlayable` can be mixed with a clip; pausing a node stops its internal time; the PlayableGraph Visualizer is a discontinued experimental tool. — [Playables Examples](https://docs.unity3d.com/2022.3/Documentation/Manual/Playables-Examples.html)
- `AnimationLayerMixerPlayable`: "controls an animation layer mixer"; `SetLayerAdditive` ("Additive layers blend with previous layers"), `SetLayerMaskFromAvatarMask`, `IsLayerAdditive`. — [AnimationLayerMixerPlayable](https://docs.unity3d.com/2022.3/Documentation/ScriptReference/Animations.AnimationLayerMixerPlayable.html)
- Animation C# Jobs (Unity 2018.2): `AnimationScriptPlayable` "contains an animation job and acts as a proxy between the PlayableGraph and the job"; `IAnimationJob` gives `ProcessRootMotion` (always first) and `ProcessAnimation`; `AnimationStream` exposes `deltaTime`, root motion, `AsHuman()`, `GetInputStream()`; handles `TransformStreamHandle`, `PropertyStreamHandle`, `TransformSceneHandle`, `PropertySceneHandle`; code "will run during PlayableGraph processing, in a separate thread"; shipped examples: LookAt, TwoBoneIK, FullbodyIK, Damping (tail/ponytail), SimpleMixer, WeightedMaskMixer; a MonoBehaviour foot-lock would instead run "in the main thread, and not until the animation pass is over". — [Animation C# Jobs blog](https://unity.com/blog/engine-platform/animation-c-jobs)
- Animancer: aimed at "Anyone who dislikes the restrictiveness of Animator Controllers"; current API v8.4; Lite and Pro editions. — [Animancer introduction](https://kybernetik.com.au/animancer/docs/introduction/)
- Six claimed Mecanim problems: Simplicity ("Everything requires extra steps" vs "Just get the AnimationClip you want and tell Animancer to play it"); Transparency ("Animancer Pro gives you full access to its source code so you can see what it's doing"); Adaptability ("All the animation logic for a character must always be defined in exactly one Animator Controller"); Safety (string names outside code; "Directly referencing the animations you want to play minimises your external dependencies"); Clarity ("Scripts define all their logic and requirements"); Reliability (Mecanim can ignore or delay commands; Animancer "Always does exactly what your scripts tell it to do"). — [Why Replace Mecanim?](https://kybernetik.com.au/animancer/docs/introduction/mecanim-vs-animancer/why)
- Animancer "can play alongside Animator Controllers"; "Animancer can be more efficient than other systems if used correctly, though in most cases the differences are small enough not to matter either way." — [Mecanim vs Animancer](https://kybernetik.com.au/animancer/docs/introduction/mecanim-vs-animancer)
- Animancer layers: "Layers start at Weight = 0 by default"; each layer "can be given an AvatarMask"; "each layer will override the previous layer, entirely replacing its output" unless `IsAdditive = true`; fade the layer rather than the state. — [Animancer Layers](https://kybernetik.com.au/animancer/docs/manual/blending/layers/)
- Animancer's Unity-bug list: "Animator.stabilizeFeet gets set to false during the first update when using playables"; Timeline "Root Motion doesn't work properly" with playables; minor timing inconsistencies vs Mecanim. — [Animancer Unity Bugs](https://kybernetik.com.au/animancer/docs/bugs)

### Inferences
- The "spaghetti" problem as documented by Animancer is really three things: (1) transition graphs scale quadratically with states, (2) logic is split between an asset and scripts that reference it by string, (3) the asset evaluates commands with its own latency rules (exit time, interruption source). Studios bypass Animator Controllers to get a plain function call `Play(clip, fadeSeconds)` and keep decision logic in code.
- Nothing is lost by bypassing: AnimationMixerPlayable is the crossfade, AnimationLayerMixerPlayable is the layer stack with masks/additive, AnimatorControllerPlayable lets you keep a controller as one node. For a robot, this is the argument for a small code-driven "which clip, what weight" layer instead of a graphical state machine.
- Animation C# Jobs show where Unity puts procedural corrections: inside the pose pipeline, threaded, before transforms are written, not in a MonoBehaviour after the fact.

### Gaps
- Animancer's own page does not state it is built on Playables (it is, from general knowledge, but the fetched pages do not say so).
- No independent benchmark comparing Animator Controller vs Playables evaluation cost was found.

## Q4. Motion matching in Unity: Kinematica, MxM, Motion Symphony, 2024-2026 packages

### Takeaway
Kinematica (Unity Labs) shipped as 0.4-0.8 preview packages for 2019.3/2020.2, last updated August 2020, and was never promoted; it replaced graphs with a nearest-neighbour pose+trajectory search but had no layering/partial-body support. The production option became MxM (Vault Break Studios; Motion Symphony is its Unreal port), now a community-maintained fork; 2025-2026 brought open-source Unity 6 packages (Ponton's MotionMatching from SIGGRAPH Asia 2025 work, Kinema) and a "Learned Motion Matching" asset on Sentis. No first-party Unity motion matching exists as of this research.

### Cited Findings
- Kinematica "allows to create animated character from raw unstructured motion data (animation clips or motion capture data)"; "We only wrote the game logic for this demo and Kinematica produces the animation poses at runtime"; version 0.8.0-preview, requires Unity 2019.3; content "early, incomplete, work-in progress". — [Kinematica 0.8 manual](https://docs.unity3d.com/Packages/com.unity.kinematica@0.8/manual/index.html)
- Concepts: pre-processing samples clips at a target framerate into a motion library; "Tags and markers are a concept that allows to associate user defined semantic trait with sequences"; "Kinematica relies on the movement of the animated character to be based on trajectories"; each frame it "performs a nearest neighbor search in an unstructured library of related skeletal poses" against current pose and desired trajectory; tasks "always execute in its own job prior to the frame update"; Snapshot debugger records state each frame for rewind. — [Kinematica Overview 0.6](https://docs.unity3d.com/Packages/com.unity.kinematica@0.6/manual/Overview.html)
- Package description: "a considerably improved version of Motion Matching that achieves a near constant time lookup for arbitrary complex motion databases and does not rely on parameter tweaking or magic numbers"; "This package is still in an experimental stage". — [needle-mirror com.unity.kinematica](https://github.com/needle-mirror/com.unity.kinematica)
- Unite Now session (May 7, 2020), Unity staff (DavidGeoffroy) answers: "Kinematica currently only plays one segment at a time"; "Kinematica itself doesn't support partial animations at the moment"; layering "is not where we have invested the brunt of our efforts"; for VR head/hand puppeteering "I don't think Kinematica will perform well (or at all) in your use case"; "Kinematica doesn't generate motion, so your results will be as smooth as your input motion". — [Unite Now Kinematica thread](https://discussions.unity.com/t/unite-now-kinematica-democratizing-motion-matching-for-character-animation/788112)
- "What happened to Kinematica?" (Nov 19, 2021): last update "0.8.0 Experimental" on August 03, 2020; replies suggested MxM; no Unity staff reply in the thread. — [What happened to Kinematica?](https://discussions.unity.com/t/what-happened-to-kinematica/862682); the 2020.2 manual lists 0.4-0.8 as preview. — [Unity 2020.2 manual](https://docs.unity3d.com/2020.2/Documentation/Manual/com.unity.kinematica.html)
- Motion Symphony is Kenneth Claassen's Unreal plugin, "essentially a port of Motion Matching for Unity with some slight differences". — [Unreal forum](https://forums.unrealengine.com/t/motion-symphony-motion-matching-pose-matching-tools-plugin/145866/3); Xsens case study on MxM: motion matching "plots the future trajectory of the animated character rather than relying on hand-built state transitions". — [Xsens case](https://www.xsens.com/cases/transforming-game-characters-with-motion-matching-for-unity)
- MxM technical reference (community fork, self-described as "Generated from aggregated technical data"): MMData holds "Pose Database", "Trajectory Database", "Feature Vectors", KD-trees; standard joints "Hips (Root), Left Foot, Right Foot", high-fidelity adds shoulders/hands; "Prediction Points: 0.33s, 0.66s, 1.0s"; cost = pose cost + trajectory cost, normalized by Calibration Handles (e.g. 6 m/s, 180 deg/s); "Search Frequency ... Every 1-3 frames"; transitions use inertialization ("Traditional Mecanim transitions rely on cross-fading"); Required vs Favour tags; events with wind-up/action/follow-through/recovery and "Motion matching suspended; plays to completion" during action; "MxMAnimator component, which replaces Mecanim's logic while still using the Animator for mesh skinning"; upper-body blend spaces on a body mask; "MxM relies entirely on Root Motion"; "KCC must feed actual velocity back to MxM"; Burst + Jobs, search on a worker thread. — [MxM technical reference](https://motion-matching-for-unity.readthedocs.io/en/latest/technical-reference/)
- MxM fork status: "Community maintained fork" at Frost-Blade-Studios, minimum Unity 2020.3, tested 2022.3+ and Unity 6; dependencies listed as Mecanim and "Unity Physics" (for trajectory prediction). — [MxM getting started](https://motion-matching-for-unity.readthedocs.io/en/latest/getting-started/)
- Ponton's package: from the master thesis "Motion Matching for Character Animation and Virtual Reality Avatars in Unity" (2022, UPC); cite "Environment-aware Motion Matching", SIGGRAPH Asia 2025; MIT; components Motion Matching Controller + Character Controllers; docs sections on MMData, custom trajectory features, environment features, "Unity Animator Integration". — [motionmatching-docs](https://joseluisponton.com/motionmatching-docs/), [JLPM22/MotionMatching](https://github.com/JLPM22/MotionMatching)
- Kinema (MIT, Unity 6000.3+): "An offline bake pipeline turns AnimationClips into a normalized feature database"; "Burst-compiled parallel job with a KD-tree option"; "parallel gait-phase channel used as an extra cost term"; blends "through a PlayableGraph"; "Inertialization transitions (Burst animation job) or two-slot crossfades"; Learned Motion Matching backend "in progress". — [nekuzaky/kinema](https://github.com/nekuzaky/kinema)
- A "Learned Motion Matching" asset ($20) requires Animation Rigging and Sentis 1.3; "Motion Matching System for Unity" ($109) lists Unity 2022+. — [Unity marketplace listing](https://marketplace.unity.com/packages/tools/animation/learned-motion-matching-312510), [Asset Store listing](https://assetstore-fallback.unity.com/packages/tools/animation/motion-matching-system-for-unity-257707)

### Inferences
- Why Kinematica was dropped is not officially stated; the record shows a preview that never gained layering/partial-body blending, a 2020 last release, and a 2021 community verdict of "suspended". Interpretation: the feature could not coexist with the layered Mecanim workflow studios need (upper-body actions, additive), and Unity's DOTS animation effort it was tied to also stalled.
- Motion matching's inputs are exactly a robot's: current joint state + a predicted root trajectory (0.33/0.66/1.0 s ahead); its output is "which stored frame to continue from" plus an inertialization blend. It is a REALISM mechanism (responsiveness, no hand-built transitions) that preserves LIFE because it only replays captured frames ("as smooth as your input motion").
- MxM's "events" (motion matching suspended during the action phase) and "favour tags" are the right pattern for authored character beats inside a reactive locomotion layer.

### Gaps
- No official Unity statement on Kinematica's cancellation or any first-party motion matching roadmap was found; one blog claim that Unity "intends to ship a native motion matching system" could not be verified.
- Exact MxM cost-function weights are not published in the fetched docs; the fork docs say to check the official UserManual.pdf.

## Q5. Physics and ragdoll blending: Final IK, PuppetMaster, ArticulationBody, ML-Agents

### Takeaway
Final IK supplies LateUpdate solvers that take the animated pose and pull it to targets and ground (FBBIK effectors with pull/reach/push, Grounder raycast foot placement with pelvis lowering, LookAtIK with per-chain weights and clamps, VRIK with a procedural stepping module); PuppetMaster then makes a ConfigurableJoint ragdoll follow that pose with muscle (joint drive) weights plus "pin" AddForce springs, and maps the result back; ArticulationBody is Unity's reduced-coordinate robot joint with explicit PD drives; ML-Agents' Walker is a physics humanoid with 39 continuous "target rotations and strengths" actions, and imitation (BC/GAIL) exists but is not documented as an animation tool.

### Cited Findings

Final IK
- Components: FBBIK ("Full Body IK system for biped characters"), VRIK, Grounder ("automatic vertical foot placement and alignment correction system"), Look At IK, Aim IK, CCD IK, FABRIK, Limb IK, Arm/Leg IK, Interaction System, rotation limits, and AnimationJobs-based CCDIKJ/AimIKJ; "Does NOT require, but works with Mecanim". — [Final IK docs index](http://www.root-motion.com/finalikdox/html/index.html)
- FBBIK "maps any biped character to a low resolution multi-effector IK rig"; effectors: hands/feet (end), shoulders/thighs (mid), body (drags thighs unless `effectChildNodes` false); each effector has `positionOffset` that "resets to zero after every solver update, so multiple scripts can add to it"; Pull per chain (full pull on one limb lets the character "be pulled from that effector without losing contact"), Reach (default 0.05), Push/Push Parent, Reach/Push Smoothing; bend goals replace missing elbow/knee effectors; iterations 0 skips full-body solve for distant characters; pose is sampled at Start to find bend directions, so limbs must be slightly bent; limitations: no finger effectors, elbows/knees are 3-DOF hemisphere-limited since 0.22, extra swing bones (wings) unsupported. — [FBBIK](http://www.root-motion.com/finalikdox/html/page8.html)
- Grounder: assumes "characters are animated on planar ground"; each foot is offset by ground height minus root height, and if negative "the solver pulls the character down from the pelvis"; variants GrounderFBBIK, GrounderBipedIK, GrounderIK (any CCD/FABRIK/Limb/Trigonometric legs, "spider or bot characters"), GrounderQuadruped; params `layers`, `maxStep`, `heightOffset`, `footSpeed`, `footRadius`, `prediction` (based on foot velocity), `pelvisSpeed`, `pelvisDamper`, `lowerPelvisWeight`, `liftPelvisWeight`, `rotateSolver` (walls/ceilings); quality Fastest = "a single raycast for each foot, plus a raycast for the root", Best = "1 raycast and a capsule cast for each foot and a sphere cast for the root". — [Grounder](http://www.root-motion.com/finalikdox/html/page9.html)
- LookAtIK: spine (ordered, skippable), head, eyes; `weight` "multiplies all the other weights"; `bodyWeight`, `headWeight`, `eyesWeight`; clamp weights "0 is free rotation, 1 is completely clamped to zero effect"; `clampSmoothing` (sine iterations), `spineWeightCurve`. — [Look At IK](http://www.root-motion.com/finalikdox/html/page13.html)
- VRIK: "a high speed full body solver dedicated to animating VR avatars", ~2-3x faster than FBBIK, 3 LODs; targets for head, hands, pelvis, feet with position/rotation weights; `bodyPosStiffness`/`bodyRotStiffness`, `neckStiffness`, `maxRootAngle`; legacy Procedural Locomotion with `footDistance`, `stepThreshold`, `angleThreshold`, `maxLegStretch`, `comAngleMlp` ("step sooner when balance is lost"), `stepSpeed`, `stepHeight`, `heelHeight`, velocity prediction; Animated Locomotion drives an 8-direction strafing blend tree via parameters `VRIK_Turn`, `VRIK_Horizontal`, `VRIK_Vertical`, `VRIK_IsMoving`, `VRIK_Speed`. — [VRIK](http://www.root-motion.com/finalikdox/html/page16.html)
- Ordering caveat from the vendor forum: AimIK by default solves before VRIK, so "at the time when AimIK reads the target positions (LateUpdate), the VRIK character is in its default pose"; fix by disabling components and calling `solver.Update()` in your own LateUpdate order; call `Physics.SyncTransforms()` after IK if Auto Sync Transforms is off. — [Final IK forum thread](https://discussions.unity.com/t/final-ik-full-body-ik-aim-look-at-fabrik-ccd-ik-1-0-released/525769)

PuppetMaster
- Architecture: Target (kinematic animated character, "usually has a character controller"), Puppet (ragdoll copy that "must use ConfigurableJoints"), Root (holds rig and Behaviours), Behaviours (adjust "muscle and pin weights, strength, and target pose"). Each joint becomes a Muscle that "maintains a reference to its animated target and automatically calculates Joint target rotations". Pins are "pinning the rigidbodies to their targets using AddForce commands" and "can be imagined as spring joints pulling each ragdoll bone towards their animated target". Mapping "can also be smoothly blended in and out for the entire character or for each Muscle separately". Modes Active/Kinematic/Disabled, blended over "Blend Time". — [PuppetMaster Overview](http://www.root-motion.com/puppetmasterdox/html/page3.html)
- Component master weights: Mapping Weight (how strongly the animated character maps onto the ragdoll pose), Pin Weight ("pinned to their animated targets using simple AddForce"), Muscle Weight ("normalized strength of the muscles"); Muscle Spring = Slerp Drive positionSpring, Muscle Damper = positionDamper; Pin Pow, Pin Distance Falloff ("Weakens pinning force the farther a target is"); Update Joint Anchors (expensive), Angular Limits, Internal Collisions ("Usually left off while pinned"); per-muscle Group, Mapping/Pin/Muscle Weight multipliers. — [PuppetMaster Component](http://www.root-motion.com/puppetmasterdox/html/page5.html)
- BehaviourPuppet: pins/unpins on collision and recovers; `collisionResistance` ("smaller value means more unpinning"), can be a curve over muscle target velocity; `knockOutDistance` ("if the distance from the muscle to its target is larger than this value, the character will be knocked out"); `regainPinSpeed`; get-up after `getUpDelay` when hip velocity < `maxGetUpVelocity`, `blendToAnimationTime`, prone/supine offsets; per-group `unpinParents/Children/Group`, `minMappingWeight`/`maxMappingWeight`; boosting (immunity, impulse multiplier). — [BehaviourPuppet](http://www.root-motion.com/puppetmasterdox/html/page10.html)

ArticulationBody
- "build physics articulations such as robotic arms or kinematic chains"; one component defines what Rigidbody + Joint would separately; root has Mass/Immovable/Use Gravity; joint types Fixed ("rigid, unbreakable and unstretchable"), Prismatic, Revolute (hinge about parent anchor X), Spherical (Swing Y, Swing Z, Twist; Free/Limited/Locked); drives with Lower/Upper Limit, Stiffness, Damping, Force limit, Target, Target velocity; "Effect = stiffness * (drivePosition - targetPosition) - damping * (driveVelocity - targetVelocity)"; stiffness 0 gives velocity-seeking, damping 0 position-seeking; Immovable only on the root; spherical cannot lock all three. — [ArticulationBody](https://docs.unity3d.com/2022.3/Documentation/Manual/class-ArticulationBody.html)
- URDF Importer builds "a hierarchy of GameObjects, where each GameObject is an ArticulationBody component representing a particular link"; ROS-TCP-Connector/Endpoint bridge topics and services; demo is Niryo One pick-and-place with MoveIt (2020). — [Unity robotics blog](https://unity.com/blog/engine-platform/robotics-simulation-is-easy-as-1-2-3)
- Robotics Hub now fronts "Simulation Pro" (URDF importer, ROS-2 support, Lidar/RGB-D/IMU sensors, headless Linux); older material "archived content on unsupported packages"; "driving ArticulationBodies directly" deferred to a later course. — [Unity-Robotics-Hub](https://github.com/Unity-Technologies/Unity-Robotics-Hub)

ML-Agents
- Walker: "physics-based humanoid with 26 degrees of freedom", 243 vector observations (limb position/rotation/velocity/angular velocity + goal direction), "39 continuous actions, which set target rotations and strengths for the joints", reward = product of velocity-match and head-direction terms, benchmark 2500; Crawler: 172 obs, 20 actions, benchmark 3000; no imitation or animation mentioned for either. — [Learning-Environment-Examples](https://github.com/Unity-Technologies/ml-agents/blob/main/docs/Learning-Environment-Examples.md)
- Imitation: "BC trains the Agent's policy to exactly mimic the actions shown in a set of demonstrations"; GAIL "uses an adversarial approach to reward your Agent for behaving similar to a set of demonstrations" and "works well when there are a limited number of demonstrations"; GAIL "can be mixed with an extrinsic reward signal"; warning about survivor bias, recommend "a low strength GAIL reward signal and a sparse extrinisic signal"; demonstrations are recorded "from the Unity Editor or build, and saved as assets"; no mention of character animation. — [ML-Agents Overview](https://github.com/Unity-Technologies/ml-agents/blob/main/docs/ML-Agents-Overview.md)
- One student project used ML-Agents with GAIL to control character state and reported GAIL "yielded more consistent improvement" (single unreviewed PDF). — [MLStates Agents Evaluation](https://kaisei-fukaya.github.io/files/MLStates%20Agents%20Evaluation.pdf)

### Inferences
- PuppetMaster is the clearest game analogue of a tracking controller: the animated pose is the reference, Muscle Weight/Spring/Damper are PD gains on joint drives, Pin Weight is a task-space spring on each link, Mapping Weight is how much of the simulated result is shown. Its three master weights are the three dials a robot needs: joint-space tracking gain, task-space correction gain, and "how much reality to accept back".
- BehaviourPuppet's logic (unpin on impulse above resistance, knock-out if tracking error exceeds a distance, regain pins at a rate, get up when hip velocity is low) is a complete, parameterized fall-and-recover supervisor.
- ArticulationBody drives are literally PD position/velocity targets with force limits, the same interface as a servo; Final IK/PuppetMaster targets could be sent straight to them in sim.
- ML-Agents is used for locomotion learning in Unity, not as an animation layer; the Walker's action space (target rotation + strength per joint) is the only Unity place where "muscle strength" is a per-step control.
- LIFE vs REALISM: Final IK (all solvers) = REALISM; PuppetMaster = REALISM with LIFE side effects (physical jiggle, reactions); ArticulationBody = REALISM; ML-Agents = REALISM (learned balance).

### Gaps
- The fetched Grounder page does not say whether Grounder runs before or after the main IK solver.
- The PuppetMaster pages do not define Alive/Dead/Frozen states by those names (only Active/Kinematic/Disabled modes).

## Q6. Procedural life: idle variation, look-at, breathing, springs, procedural walkers, Timeline

### Takeaway
"Life" in Unity practice is layered on top of authored clips with cheap mechanisms: random/sequenced idle variations chosen by a float into a blend tree at clip end, Cycle Offset to desynchronize cycles, additive layers for breathing, Multi-Aim/LookAtIK for gaze, spring-bone components for follow-through, and foot-target stepping controllers for legged creatures; Timeline is the tool for authored cinematic sequences.

### Cited Findings
- Idle variation: blend trees accept only float parameters; users pick an idle by setting a float to `Random.value`; fire an event near the end of each idle clip and change the parameter there, smoothing with `Mathf.MoveToward`; clips must loop or the random idle freezes. — [Random float parameter](https://discussions.unity.com/t/random-float-parameter-for-idle-animations/66633), [smooth transitions thread](https://forum.unity.com/threads/smooth-transitions.534047/), [random idle with blend tree](https://forum.unity.com/threads/random-idle-with-blend-tree.777506/)
- A shipped controller (Opsive UCC) implements idle as a blend tree driven by an integer-valued float with "random or sequential variation selection and min/max duration settings". — [Opsive Idle ability](https://opsive.com/support/documentation/ultimate-character-controller/character/abilities/included-abilities/idle/)
- Cycle Offset is a per-state, parameter-drivable "offset added to the state time of the motion"; Mirror flips humanoid clips. — [Animation State](https://docs.unity3d.com/2022.3/Documentation/Manual/class-State.html)
- Additive layers need clips containing "the same properties as the previous layers"; Direct blend trees are suggested for facial blend shapes and additive mixes. — [Animation Layers](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-layers), [Direct Blending](https://docs.unity3d.com/2022.3/Documentation/Manual/BlendTree-DirectBlending.html)
- Secondary motion: Dynamic Bone (commercial) simulates its own particles (not Unity physics), one fixed "Root", runtime `SetWeight()`, a "Force" parameter, "does not work with rigid bodies". — [Dynamic Bone thread](https://discussions.unity.com/t/dynamic-bone-realistic-swaying-ponytail-and-bouncing-boobs/537434); Unity-Chan Spring Bone is "a spring bone system for lightweight secondary animations". — [com.unity.springbone on OpenUPM](https://openupm.com/packages/com.unity.springbone/); Unity's own Damped Transform / Jiggle Chain constraints cover the same need inside Animation Rigging (see Q2).
- Procedural spider (PhilS94): legs are hinge chains with limits solved by "a simple, yet tailored, CCD"; "A leg desires to step if the IK solver can not solve the leg sufficiently anymore, that is up to a set tolerance"; a central manager grants steps; two gaits: queue-based ("respects neighbouring asynchronous legs") and "Alternating Tetrapod Gait" (two groups stepping in alternate time windows); step target = anchor in body frame, extended by predicted travel, then raycasts (down/out/in) find the real surface; body "elevates and rotates in correspondence to the legs heights"; sphere casts for terrain/walls and "fake gravity in respect to its current normal". — [Unity-Procedural-IK-Wall-Walking-Spider](https://github.com/PhilS94/Unity-Procedural-IK-Wall-Walking-Spider)
- The Asset Store successor: a leg steps "when the IK solver can no longer reach its target", body rises/tilts with legs, and "procedural animation is inherently more expensive than regular animation mostly due to the IK solving and the ray casting". — [Procedural Spider asset](https://assetstore-fallback.unity.com/packages/tools/animation/procedural-spider-267789); another prototype uses "a tripod walk pattern and raycasting to allow each of its 8 legs to find its footing". — [Chunk-of-Procedural-Animation wiki](https://github.com/HangyBoi/Chunk-of-Procedural-Animation/wiki)
- VRIK's procedural locomotion (step when target is farther than `stepThreshold`/`angleThreshold` or leg stretch exceeds `maxLegStretch`, step sooner as COM angle grows) is the same stepping rule applied to a biped. — [VRIK](http://www.root-motion.com/finalikdox/html/page16.html)
- Timeline 1.8.13: "Use Unity's Timeline to create cinematic content, gameplay sequences, audio sequences, and complex particle effects"; a sequence "consists of a Timeline asset and a Timeline instance"; the Playable Director that drives it "is primarily used by the Unity Timeline package". — [Timeline manual](https://docs.unity3d.com/Packages/com.unity.timeline@1.8/manual/index.html), [Playables API](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/playables)

### Inferences
- Unity has no built-in "idle variation" feature; it is a convention: a looping base idle, a Direct or 1D blend tree of variants, an animation event at the end of each variant to re-roll, and Cycle Offset so multiple characters do not sync. All LIFE.
- Breathing/sway is an additive layer with a low weight; gaze is Multi-Aim (Rigging) or LookAtIK with clamps; both are cheap and composable because they are weight-driven post-processes.
- The procedural walker pattern is universal across the sources: per-leg anchor in body frame, step trigger (distance/unreachable), gait gate (which legs may step now), raycast to find ground, body height/tilt from foot heights. This is a REALISM mechanism with LIFE knobs (step height curve, overshoot).

### Gaps
- No Unity-authored tutorial on idle variation or breathing was found; the evidence is forum practice and one commercial controller.
- Timeline's animation-track blending rules (track offsets, ease in/out versus the Animator Controller) were not on the fetched page.

## Q7. Unity's recommended locomotion structure (Starter Assets) and known failure modes

### Takeaway
Unity's Starter Assets ThirdPersonController is a minimal, widely copied template: a CharacterController moved by script, an Animator with five parameters (Speed, MotionSpeed, Grounded, Jump, FreeFall), a 1D "Idle Walk Run Blend" tree on Speed, speed smoothed by Lerp with a SpeedChangeRate, and animation events for footsteps/landing; its known failure modes are the generic Mecanim ones (parameter ownership conflicts, blend tree mismatches with other armatures, Write Defaults).

### Cited Findings
- Parameters hashed once: `_animIDSpeed = Animator.StringToHash("Speed");` plus "Grounded", "Jump", "FreeFall", "MotionSpeed"; `_speed = Mathf.Lerp(currentHorizontalSpeed, targetSpeed * inputMagnitude, Time.deltaTime * SpeedChangeRate);` then `_speed = Mathf.Round(_speed * 1000f) / 1000f;`; `_animationBlend = Mathf.Lerp(_animationBlend, targetSpeed, Time.deltaTime * SpeedChangeRate);` sent via `_animator.SetFloat(_animIDSpeed, _animationBlend);` and `_animator.SetFloat(_animIDMotionSpeed, inputMagnitude);`; `Grounded = Physics.CheckSphere(spherePosition, GroundedRadius, GroundLayers, ...)` then `_animator.SetBool(_animIDGrounded, Grounded);`; Jump/FreeFall bools cleared when grounded, FreeFall set after a fall timeout. — [ThirdPersonController gist](https://gist.github.com/bzgeb/715653b15b143a243a7992c5f4d6c5b1)
- The Starter Assets Animator has a blend tree "Idle Walk Run Blend" on Speed with Idle at 0, Walk_N at 2, Run_N at 6 (Japanese tutorial, secondary source). — [Zenn article](https://zenn.dev/sumeragi_0258/articles/5d98f67fc3f3e9); clips live under `Assets/StarterAssets/ThirdPersonController/CharacterAnimations`. — [Medium article](https://medium.com/@ricardoemiranda/how-to-repurpose-unitys-third-person-character-controller-animations-for-your-own-game-e4a9f99ceedc)
- A third-party integration forum notes conflicts when two scripts "compete for control over the Animator's 'Speed' parameter". — [Adventure Creator forum](https://adventurecreator.org/forum/discussion/comment/46047/)
- Older Unity-support advice for a blend-tree glitch on a different armature was to switch to 2D Freeform Directional. — [Unity forum 506068](https://forum.unity.com/threads/unity-blend-tree-weird-transition-bug.506068/)
- Write Defaults mixing, blend-tree snap on transition, and stale defaults on pooled objects are documented failure modes (see Q1). — [VRCFury](https://vrcfury.com/technical/wd)
- Unity's own guidance on transitions: align foot contacts (white line in the transition graph) so "a smooth transition avoids foot slips, jumps in animation, and preserves the dynamics of the motion"; blend tree clips must share timing ("the left foot hits at 0.0 and the right foot at 0.5"). — [Transitions](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/class-transition), [Blend Trees](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-blend-trees/class-blend-tree)
- Motion-matching vendors describe the alternative structure: MxM's locomotion search drives legs/hips while "Upper-body blend spaces" run on a mask; the character controller "must feed actual velocity back". — [MxM technical reference](https://motion-matching-for-unity.readthedocs.io/en/latest/technical-reference/)

### Inferences
- The recommended pattern is "script owns physics and decides; Animator only renders": the Animator receives smoothed scalar commands (Speed) and booleans (Grounded, Jump, FreeFall), never raw input. The smoothing (`SpeedChangeRate`) is what hides blend-tree jumps.
- Failure modes to carry over: (1) two writers for one parameter, (2) clips in a blend tree with mismatched phase, (3) exit-time transitions that cannot be interrupted when the world changes, (4) defaults captured at enable time, (5) foot sliding when root motion velocity and the controller's velocity disagree.
- No distinct Unity "Gameplay Animation" sample beyond Starter Assets, the Kinematica Biped Locomotion sample, and the Animation Rigging samples was found; I treat "Gameplay Animation demos" in the brief as those.

### Gaps
- The gist does not include `OnFootstep`/`OnLand` event handlers (they exist in the official package, but I could not cite them).
- An official Unity description of the Starter Assets Animator Controller layout was not found; the 0/2/6 thresholds come from a secondary tutorial.

## Q8. Unity animation concepts on real robots

### Takeaway
The only documented end-to-end case is The Robot Engine (Bartneck et al., RO-MAN 2015): Mecanim Animator Controllers and Humanoid Avatars animate a GameObject rig whose joint angles are converted, clamped and sent over USB serial to Arduino servos on a 6-DoF LEGO figure and a 25/26-DoF InMoov. Disney Research's bipedal character uses the same layered idea (background idle, triggered clips, joystick additive offsets, RL policy underneath) but in its own engine with Maya, not Unity; Engineered Arts uses its own Tritium timeline tool; Unity's robotics effort (Robotics Hub, ArticulationBody, ROS 2) is simulation, not animation-to-hardware.

### Cited Findings
- TRE: an `AnimatorScript` "manages the Animator component that is part of Unity 3D's Mecanim Animation System" and sends GameObject positions/angles to a `ModelScript`, which converts absolute positions into relative joint positions, derives servo angles, and applies physical constraints (head limited to 180 degrees); `SerialCommunicationScript` maps each GameObject to an Arduino servo pin; Arduino firmware "simply directs the servos to the desired angle"; per-servo config = pin, min angle, max angle, initial position, reverse flag; Humanoid Avatars are used for mapping ("humanoid does not necessarily mean that the robot must have a human shape"); the state machine "allows the animator to define the transitions between animation states" so a robot can be restricted to certain transitions; robots: LEGO Fireman (6 DoF) and InMoov (25 DoF, 26 GameObjects); limitations: Arduino-only, no user study, no serial rate stated. — [The Robot Engine (RO-MAN 2015)](https://www.bartneck.de/publications/2015/unity/index.html)
- Disney bipedal character (arXiv 2501.05204): three runtime layers: "Background" looped idle (eye-blinking, antenna), "Triggered" operator clips blended over it (0.1 s for show functions, 0.35 s for body; "facial expressions associated with the show functions naturally blend faster than the body animation"), and "Joystick" where "The joystick axes are mapped to additive offsets to the animated head and torso pose"; the animation engine outputs a target state converted to policy commands (standing: head/torso height and orientation offsets; walking: head offsets + path velocity and angular rate); "we ignore the leg joint positions, which are not part of the policy inputs"; references are made feasible with inverse dynamics and MPC; "The policy deviates from the reference trajectory and contact schedule to recover and maintain balance"; episodic motions authored in Maya, gaits from a procedural gait tool. — [Design and Control of a Bipedal Robotic Character](https://arxiv.org/html/2501.05204v1)
- Engineered Arts' Tritium glossary defines animation Projects, Clips, Timelines and Keyframes; no Unity mention. — [Engineered Arts docs glossary](https://docs.engineeredarts.co.uk/guide/glossary)
- Runtime humanoid retargeting in Unity can be done by copying quaternions or via `HumanPoseHandler`. — [fengkan/RuntimeRetargeting](https://github.com/fengkan/RuntimeRetargeting); a hobby "ServoAnimator" Unity project animates up to 8 servos with Arduino playback from SD. — [ServoAnimator](https://github.com/Napalm1432/ServoAnimator)
- HAVEN is a Unity-based virtual robot environment for HRI/AR research (simulation, not hardware control). — [HAVEN arXiv](https://arxiv.org/pdf/2011.03464)
- Unity robotics: URDF -> ArticulationBody hierarchy, ROS-TCP-Connector, Simulation Pro with ROS 2; no animation-to-robot content. — [Unity robotics blog](https://unity.com/blog/engine-platform/robotics-simulation-is-easy-as-1-2-3), [Unity-Robotics-Hub](https://github.com/Unity-Technologies/Unity-Robotics-Hub)

### Inferences
- TRE validates the simplest path: Unity's state machine and blending as the "which pose now" generator, joint angles read from transforms, clamped per servo, streamed to firmware that only tracks setpoints. It had no feedback from the robot and no physics, so it is a LIFE-only pipeline.
- Disney's structure is the mature version of the same idea and matches Unity's layer semantics one-to-one: Background = base layer, Triggered = override/additive layers with per-region fade times, Joystick = Override Transform-style additive offsets, and the RL policy = the REALISM stage that is allowed to deviate from the reference. The explicit decision to drop leg joint angles from the animation interface and send only head/torso offsets + velocity commands is the key architectural choice.

### Gaps
- No public case of Final IK, PuppetMaster, Animation Rigging or motion matching driving physical hardware was found.
- Whether Disney or Engineered Arts use Unity anywhere in authoring could not be confirmed (no mention in the fetched sources).

## Lessons for a layered robot controller

### Takeaway
Borrow Unity's separation of concerns and its weight-everywhere discipline, not its graphical state machine.

### Cited Findings
- Layer semantics (Override replaces previous layers; Additive adds; masks give higher layers precedence per body part) and per-constraint/per-rig Weight are the documented blend primitives. — [Animation Layers](https://docs.unity.com/en-us/engine/current/manual/animation-section/animation-mecanim/animation-animator-controller/animation-state-machines/animation-layers), [Rigging Workflow](https://docs.unity3d.com/Packages/com.unity.animation.rigging@1.3/manual/RiggingWorkflow.html)
- Disney's runtime sends the policy only head/torso offsets and velocity commands, not leg angles. — [arXiv 2501.05204](https://arxiv.org/html/2501.05204v1)
- PuppetMaster exposes Mapping/Pin/Muscle weights plus Spring/Damper as the blend between animation and physics. — [PuppetMaster Component](http://www.root-motion.com/puppetmasterdox/html/page5.html)

### Inferences
- Represent a pose the Mecanim way: COM "body transform" (world) + joint vector relative to it (muscle space with per-joint ranges) + foot-contact targets. Root motion = ground-plane delta of the COM; that delta is the velocity command, exactly as Unity extracts it.
- Keep stage order fixed and weight-driven: parameters -> clip selection (code, not a graph) -> blend (1D/2D by speed/turn) -> layer composite (base locomotion; override gestures; additive breathing/idle) -> root motion -> IK/foot placement -> damping/secondary -> physics/balance policy. Every stage has a 0..1 weight so "more realism" or "more character" is a fade, not a mode switch.
- Expose exactly Unity's four parameter types to the behaviour layer (float, int, bool, trigger-with-auto-reset); the controller never sees raw sensor input, only smoothed scalars (Starter Assets' SpeedChangeRate lerp).
- Transition rules worth copying: normalized exit time with per-loop re-evaluation, fixed-duration crossfades, an explicit interruption policy per transition, and foot-contact alignment between clips in a blend (same phase at 0.0 and 0.5).
- Treat the balance controller as PuppetMaster treats physics: the animation is a reference, joint drives track it with tunable stiffness/damping, task-space "pins" pull key links (feet, head) toward targets, and a supervisor (BehaviourPuppet logic) lowers tracking when impulses exceed resistance, declares a knock-out when error exceeds a distance, and regains tracking at a rate once velocity is low.
- Like Disney and Kinematica's limits, do not hand the physics layer leg joint angles from clips; hand it COM/head/torso offsets, gait velocity, and foot targets, and let it deviate to stay up.
- Life goes in cheap post-stages: additive breathing layer, look-at with clamp weights and a spine weight curve, damped-transform follow-through on appendages, random idle re-rolled by an end-of-clip event, Cycle Offset against sync.
- Motion matching is the upgrade path for locomotion once there is a clip library: inputs are current joint state and a 0.33/0.66/1.0 s predicted trajectory, output is a clip frame plus inertialized blend; keep an "event" mode that suspends matching during authored beats.
